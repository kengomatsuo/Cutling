# Release workflow

1. `./deploy.sh bump` (patch by default) rewrites MARKETING_VERSION **and CURRENT_PROJECT_VERSION** in every shipping build config and leaves CutlingUITests alone. App Store Connect tracks build numbers **per platform** and rejects any that is not higher than that platform's last upload, so the single shared counter must exceed BOTH (macOS was already at 14 while iOS was at 1, hence the jump to 15 for 1.5.3).
2. Edit the **two** App Store "What's New" sources. iOS and macOS carry **different** copy and live in separate metadata trees:
   - `fastlane/metadata/en-US/release_notes.txt` is the **iOS** App Store. iOS-relevant items only; never list macOS-only features (Mac welcome screen, global hotkey, menu bar picker, auto-update) here.
   - `fastlane/metadata_mac/en-US/release_notes.txt` is the **macOS** App Store (the `Cutling` target's `mas` build). macOS-relevant items only. (The direct-download `dist` + Sparkle build is a separate channel and has no App Store listing.)
   - Scope each to the delta over what is LIVE on that platform (a platform's live version can differ from the other's).
3. Every other locale's notes are written blind from a meaning brief, one writer per few languages, never translated from the English (the `blind-translation` skill; 2.0's brief, words and apply script: `docs/aso/events/2.0-strings-brief.md`, `docs/aso/events/2.0-locales/`, `scripts/apply-2.0-words.py`). `./deploy.sh release_notes` and `release_notes_mac` machine-translate the English over every locale, so they are not run on notes already written that way.
4. Binaries build on Xcode Cloud, never on the shared Mac: push, then start the hand-started **Release** workflow (`a342d701-f9de-4c42-b493-6e3fbb302906`, product `F7610AA8-F110-4FB9-9DC6-543266C2B62E`; both archives `APP_STORE_ELIGIBLE`) with `POST /v1/ciBuildRuns` on main's git reference `ef398983-1f7a-4da3-bc96-2359ba46fc1a` (Undirect's `Support/AppStore/asc_api.py` signs the call). Xcode Cloud numbers each build by its run, overriding `CURRENT_PROJECT_VERSION`, so the Mac upload is refused until the run number passes the Mac's last build: set Next Build Number in App Store Connect, Xcode Cloud settings, above both platforms' last uploads. The older "Default" workflow only feeds internal TestFlight. Store text and screenshots still go up with `./deploy.sh metadata` and `metadata_mac`.
5. On the day the version is live on the store, set `web/_generator/live.py` to what it has (`LIVE_CAPS`, and each `LIVE_FEATURES` entry such as `"fill-ins"`), then `./deploy.sh web`: the site and the AI files say only what the live app does.

To correct notes on a version already submitted for review, use `./deploy.sh resubmit_notes` (cancels the in-review submission, re-uploads metadata, resubmits; resets the review queue).

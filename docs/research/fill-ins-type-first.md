# Fill-ins: type the value first, then tap the cutling (card ASG102)

Question: can Cutling fill a blank from text the person typed before tapping the cutling ("Sarah", switch to Cutling, tap "Reply", get "Hi Sarah, your ...")? Every finding below carries its URL and the date it was fetched (2026-11-21, all fetches in this run); saved copies and the row list are in `fill-ins-type-first-src/` (`notes.md`). Chrome was used read-only, in one own tab (closed), for the Typinator help centre and the Apple Developer Forums, which render in JavaScript. Design opinions are marked GUESS, anything not confirmed UNSURE.

## What Cutling does today with the text before the cursor

Read in the working tree on 2026-11-21 (`CutlingKeyboard/KeyboardViewController.swift`, `FillInPanel.swift`, `docs/fill-ins-flow.md`):

- `refreshWordBeforeCursor()` stores `trailingWord(in: documentContextBeforeInput)`: the run of letters, digits, `_` and `-` at the very end. A trailing space gives an empty word; an apostrophe ends the word ("O'Brien" gives "Brien").
- `wordMatches` offers only cutlings whose name starts with that word (2+ characters). Tapping one calls `use(_, replacingCount: word.count)`, which does `deleteBackward()` once per typed character and types the cutling. That is the "replaces the typed word" path (abbreviation expansion). It never feeds the word into a blank.
- The fill-in path already reads typed text: `FillSession.typedValue(in:)` finds the text Cutling typed last (`tail`) in the context and takes everything after it; `fillNext()` stores it and trims a trailing space before punctuation. So "value typed with the person's own keyboard, read back from the context" exists, but only AFTER a blank is shown. Type-first reads the same context BEFORE the cutling is typed, so there is no `tail` to anchor on: the rule has to say where the value starts.

Take: (a) the two products that read text before the caret (Keyboard Maestro, Typinator, Espanso regexes) leave the boundary to a pattern the author writes, which is why they need no default and why a non-match simply does nothing; (b) the only product with a built-in rule is Raycast's keyboard: selection first, else the whole field. (c) Every tool with a form keeps the empty case safe by making the field required or leaving a visible blank, none swallows text silently.

## 2. How reliable the text before the cursor is in a keyboard extension

| Finding | Source and date |
|---|---|

Apple states no length limit and no nil rule. SDK header marks `selectedText` `API_AVAILABLE(ios(11.0))` (saved in `fill-ins-keyboard-apis-sources/sdk_headers_iOS27.2.txt`). | https://developer.apple.com/documentation/uikit/uitextdocumentproxy/documentcontextbeforeinput and `/selectedtext` (JSON saved), 2026-11-21 |

Reading for the design: a short value on the caret's own line (one word, or a short selection) is the case every report treats as working; pastes, multi-line text and web fields are where it breaks. The existing `FillSession.typedValue` already guards against a cut-short context by matching a shorter tail; type-first has no tail, so it needs its own guard (below).

## 3. Recommendation (all GUESS unless a finding above is named)

**Rule, in order (GUESS)**
1. Only a cutling whose first blank is a free-text blank or a choice blank takes typed text; cutlings without blanks stay as today.
2. If `selectedText` is non-empty and under 60 characters and has no line break: that is the value (the person chose the boundary, as Raycast's keyboard does; finding: Raycast iOS). Replace it by typing over it: `insertText` over a selection is the normal UIKeyInput behaviour (UNSURE through the proxy; device check).
3. Else the last word of the before-context, using the existing `trailingWord` plus one change: allow one trailing space (autocorrect and suggestions add one, so today's `wordBeforeCursor` is empty right after "Sarah "), and delete that space with the word.
4. Never the text since the last line break. Why (GUESS): the person who types "Thanks for waiting. " then taps a snippet would lose the sentence; the context holds a line at best (KeyboardKit #281, #584) and cannot be trusted over a paste (threads 772158, 812642).
5. Choice blank: take the word only if it matches a choice, ignoring case and diacritics; otherwise do not claim it.
6. Verify before deleting: re-read the before-context and require that it ends with the value (trimmed, because of the leading-space report, thread 700446); delete one grapheme per `deleteBackward()` as `use` does; on a mismatch fall back to the panel. Avoid the fast delete-then-insert loop in web fields by deleting first, then typing the whole cutling in one `insertText` (WebKit 179602).

**Several blanks (GUESS)**: type-first fills only the first blank in the text; the other blanks go through the normal panel, which already remembers values. Reason: a separator is a trap for names ("Lee, Sarah"), addresses and Indonesian prose with commas (Espanso writes its comma into the regex for that reason: finding 1). If the owner wants more: a selection of several lines, one value per line, is the one separator people do not type by accident; no tool in section 1 does this, so it would be new and untested.

**How the person learns it (GUESS)**: no setting to read. First time a cutling with blanks is tapped and a usable word sits before the caret, the panel for blank 1 shows that word as a chip ("Sarah") above the saved values; one tap fills and moves on. After the person has tapped that chip three times, the next tap on such a cutling skips the panel for blank 1 and shows a short "Used Sarah. Undo" bar (Snippety already has an undo bar after insert, `fill-ins-design/README.md`). One sentence in the fill-in section of the editor's help and in What's New once fill-ins ship (they are off in every build today, `docs/fill-ins.md`). This keeps the first use visible and reversible, and the cost of a wrong guess is one tap.

**Fallback (GUESS)**: empty or nil context, a context that does not end in a word, a word over 40 characters, a choice that does not match, or a failed verify: nothing is deleted, the existing panel for blank 1 appears with "Type with Your Keyboard" as today. The chip is simply absent. Secure and phone fields never reach Cutling (Apple guide).

**Device checks before trusting it (UNSURE items)**: Messages, Notes, Mail, Gmail app and web compose, WhatsApp, Safari search field and a contenteditable page: (1) type "Sarah " and read the context after the globe switch; (2) select a word and read `selectedText` and the before-context; (3) one tap to fill and compare the field. Expected failure sites from the reports: Gmail and Mail after a paste, web fields.

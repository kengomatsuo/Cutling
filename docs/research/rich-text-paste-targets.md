### Which is most common

- **Highlight: `==text==`** is the clear majority: Obsidian, Typora, Bear 2, iA Writer, Joplin (default on), Craft, Tiptap, markdown-it-mark, and pandoc's `mark` extension. The holdouts are Ulysses (`::mark::`, which Craft also accepts) and the products with no highlight at all (CommonMark, GFM, Slack, Discord). The HTML fallback is `<mark>`.
- **Underline: no majority.** `<u>` raw HTML is what Typora, Tiptap and Notion's API document, and what pandoc and Apple's HTML reader accept. `++text++` (markdown-it-ins → `<ins>`) is Joplin's opt-in and what **Apple Notes' own Markdown export writes**, but Ulysses uses `++` for comments and GitHub's sanitizer is the only place `<ins>` is preferred over `<u>`. Bear 2's `~text~` collides with strikethrough: the GFM spec says "two tildes", but Apple's parser strikes a single `~` too (local test below). Discord's `__text__` collides with CommonMark bold. Pandoc's `[text]{.underline}` exists only in pandoc.
- **What Cutling's own parser does with them** (local run of `AttributedString(markdown:)` on the macOS 27 SDK, 2026-11-22, `scratchpad/q4/md.swift`), input `a ==hi== ++ins++ ~one~ ~~two~~ <u>u</u> <mark>m</mark> [x]{.underline}`, with both `.inlineOnlyPreservingWhitespace` and `.full`:
  - `==hi==` and `++ins++` stay literal text, with no attribute.
  - `~one~` **and** `~~two~~` both become strikethrough (`inlinePresentationIntent` 32). So Bear's `~underline~` would read as strikethrough in Cutling.
  - `<u>` and `<mark>` stay in the string as literal characters, tagged `inlineHTML` (intent 256); the text between them gets no style.
  - `[x]{.underline}` stays literal.
  - So any underline or highlight syntax Cutling picks must be handled by Cutling's own code, before or after Apple's parser; Apple's parser supplies none.

## 2. Bulleted, dashed and numbered lists; what Apple Notes puts on the pasteboard

### How Markdown-family tools write lists (read 2026-11-22)

- **CommonMark 0.31.2**: "A bullet list marker is a `-`, `+`, or `*` character"; ordered markers are digits followed by `.` or `)`. Two items are the same list only if they use the same bullet character, and "Changing the bullet or ordered list delimiter starts a new list" (`spec.txt` lines 4127-4131, 5247-5272). The rendered HTML is `<ul>` for all three bullets, so the spec keeps no visible difference between them.
- **Pandoc**: same three bullets (`MANUAL.txt` line 4547). Its AST is `BulletList [[Block]]` with no style field (`jgm/pandoc-types` `src/Text/Pandoc/Definition.hs` line 290), so which bullet was typed is lost, and its Markdown writer always writes `- ` (`src/Text/Pandoc/Writers/Markdown.hs`, `bulletListItemToMarkdown`, lines 825-839).
- **Obsidian**: "adding a `-`, `*`, or `+`"; numbered with `.` or `)` (https://obsidian.md/help/syntax). **Typora**: "`*` … can be replaced with `+` or `-`" (https://support.typora.io/Markdown-Reference/). **Bear 2**: `*` or `-` (https://bear.app/faq/how-to-use-markdown-in-bear/). **iA Writer**: `-`, `*` or `+`, tasks `- [ ]` (https://ia.net/writer/support/basics/markdown-guide). **Discord**: `-` or `*` (support article above). **Craft**: `-` or `*` make a bullet list, and `+` makes a **toggle** list (https://support.craft.do/en/write-and-edit/formatting/markdown-shortcuts.md). **Ulysses** calls its unordered lists "Dashed" ("Dashed and numbered lists can be created by simply typing dashes or numbers", https://help.ulysses.app/introduction/first-steps-markdown-xl). **Slack mrkdwn**: no list syntax at all.
- **None of these keeps "dashed" distinct from "bulleted" as a list type.** The only places found that do are Apple's: Notes, which stores Dotted 100 / Dashed 101 / Numbered 102 (below); WebKit's `Apple-dash-list` class; and `NSTextList`'s `{hyphen}` vs `{disc}`.
- **Apple Notes maps typed Markdown-style markers to its three lists**: "type a character followed by a space: an asterisk for a bulleted list … a hyphen for a dashed list, or a number and a period for a numbered list" (Notes User Guide, Notes 4.13 for macOS 27, https://support.apple.com/guide/notes/apd93c815aa0/mac). Notes' Markdown export writes Bulleted as `* ` and Numbered as `1. ` (Podfeet test, section 1). Its Markdown import, tested through Shortcuts on macOS 26.5.2, turned `-` into a dash list, `1.` into `<ol>`, and `- [ ]` / `- [x]` into checklist items (`eliotshea/notes-mcp` `docs/spike-findings.md`, "Verified Markdown support"). So Notes itself treats `* ` = Bulleted, `- ` = Dashed, `1. ` = Numbered, in typing, export and import. What its export writes for a Dashed list is not in any source read here (presumably `- `). UNVERIFIED.

### Apple's own markup for a dashed list

- **WebKit names it.** `Source/WebCore/editing/TextListParser.cpp` (apple-oss-distributions/WebKit, tag WebKit-7624.2.5.11.4, read via GitHub API 2026-11-22) is WebKit's "Smart Lists": in an editable web view, typing a marker then a space turns the line into a list. `*` or `•` makes a disc list; `-` (hyphen-minus) makes a dash list whose `list-style-type` is the string em dash + two no-break spaces (`U+2014 U+00A0 U+00A0`); `1.` or `1)` makes a decimal list with `start`. The list element gets a class: `Apple-disc-list`, `Apple-dash-list` or `Apple-decimal-list` (`classNameForSmartList`, lines 176-189), plus an inline `style="list-style-type: …"`. So Mac Mail and any WebKit editor with Smart Lists on write a dashed list as `<ul class="Apple-dash-list" style="list-style-type: '—  '">`. (The comment above `parseTextList` says U+2010, but the code checks U+002D.)
- **Notes writes the same class.** A decompile of iOS 18.2's `NotesUI.framework` `ICNote(HTML)` (GitHub `EthanArbuckle/iPhone17-1_18.2_22C152_Restore`, file `System/Library/PrivateFrameworks/NotesUI.framework/ICNote(HTML).m`, read 2026-11-22) shows `htmlStringFromAttributedString:` choosing `ol` for paragraph style 102 and `ul` otherwise, and writing `<ul class="Apple-dash-list">` for style 101 (line ~302). On HTML import (`attributedStringFromHTMLString:`) Notes first injects `<style>ul.Apple-dash-list, ul.Apple-dash-list ul { list-style-type: upper-roman; }</style>` as a sentinel, parses with `NSAttributedString`, then `fixDashedListsInAttributedString:` turns those lists back into Notes dashes. So Notes' own HTML reader recognises `class="Apple-dash-list"` as Dashed. Whether its **paste** path uses this reader is UNVERIFIED (see below).
- Style numbers match Notes' storage: 100 dotted (Bulleted), 101 dashed, 102 numbered, 103 checklist (`apple_cloud_notes_parser` `lib/AppleNote.rb` lines 40-50, read 2026-11-22).
- **Real Notes HTML, from AppleScript.** The `pinto-notes/pinto-notes` test fixtures hold "`body of note` as Notes on macOS 15.7 returned it" (`PaneTests/AppleNotesImportTests.swift` lines 9-80, read 2026-11-22): Bulleted is a bare `<ul>`, Dashed is `<ul class="Apple-dash-list">`, Numbered is `<ol>`, nested lists sit inside the parent list, underline is `<u>`, strikethrough `<strike>`, headings are sized bold spans, monospace is `<font face="Courier">`. A checklist also comes out as a bare `<ul>` (their test `theHTMLAloneCannotTellAChecklistFromBullets`). That repo's own note, "Notes itself writes the numbered items as dashes", records a case where a numbered list typed straight after a dashed list came out inside the same `Apple-dash-list`. Other tools that read or write the class: `eliotshea/notes-mcp` `src/htmllist.ts`, `findus/apnotes` `lib/src/converter.rs` (rewrites every `<ul>` to `Apple-dash-list` before giving HTML to Notes), and `YuanyuanMa03/apple-notes-agent-skill` `skills/mac-notes/references/quirks.md` line 55 (writing `<ul class="Apple-dash-list">` through AppleScript creates a native Notes dashed list, and a plain `<ul>` right after one is merged into it). This is the AppleScript body, not the pasteboard.
- **Notes' plain-text form of lists** (macOS 26.5.2, from `eliotshea/notes-mcp` `docs/spike-findings.md`, last changed 2026-08-05, read via GitHub API 2026-11-22). A note body taken through Shortcuts' Get Text as `public.plain-text` writes each list line as `\t<marker>\t<text>`: `◦` U+25E6 for an unchecked checklist item, `✓` U+2713 for a checked one, `⁃` U+2043 HYPHEN BULLET for the dashed list ("ordinary dash bullets"). That is exactly `NSTextList`'s `{hyphen}` marker (section 4), which suggests Notes' Dashed list is a `{hyphen}` text list (inference). An older Drafts action by Agile Tortoise says the same for checklists shared from Notes: "checkboxes from Notes app get imported as "◦" characters with tabs", regex `/^(\t+)◦\t/gm` (https://actions.getdrafts.com/a/1Sb, about 2018, read 2026-11-22). The same spike says "The bridge marks ordered items `\t1.\t`, not a single glyph." The Bulleted marker in this form is presumably `\t•\t` (`{disc}`); no source read here prints it. UNVERIFIED.
- The same spike lists Notes' full styling vocabulary from its App Intents metadata: paragraph styles Title, Heading, Subheading, Body, Monostyled, Caption; list styles **Bulleted, Dashed, Numbered, Checklist**; character styles bold, italic, underline, strikethrough (`ApplyFormattingIntent`). "Colour and highlight are UI-only." Its §14 tested a purpose-built note: highlight was **absent** from the AppleScript `body` HTML, from the Shortcuts plain text, RTF and HTML, and from a rendered PDF, while red text and bold came through (`<font color="#FF0505">`, `\cf2`, `p.p2 {color:#fb000b}`). Writing `background-color`, the `background` shorthand or `<mark>` through those paths was stripped. The Shortcuts HTML wrote the checklist as `list-style-type: circle`.
- **What an Apple text view itself puts on the pasteboard** (local run, AppKit `NSTextView` on macOS 27 SDK, written to a private named pasteboard, 2026-11-22; program `scratchpad/q4/copy.swift`, `copy2.swift`). Types written: `public.rtf`, `NeXT Rich Text Format v1.0 pasteboard type`, `public.utf8-plain-text`, `NSStringPboardType`, `public.utf16-external-plain-text`; **no HTML**. The plain flavour is the text storage verbatim: when list paragraphs hold no marker text (TextKit 2's default, `NSTextList.includesTextListMarkers == false`), the plain flavour has **no markers at all** (`"disc one\ndash one\nnum one"`), while the RTF writer still adds `{\listtext\t\'95\t}`, `{\listtext\t\uc0\u8259\t}`, `{\listtext\t1\t}`. With markers in the text it is `"\t•\tdisc one\n\t⁃\tdash one\n\t1\tnum one"`. So a Cutling copy must write its own markers into the plain flavour; the system will not.
- **Mac Notes on the pasteboard** (2021, Obsidian forum, https://forum.obsidian.md/t/extra-characters-when-pasting-from-apple-reminders-or-notes/23266, read 2026-11-22): a user's clipboard inspection after copying from Notes found "There's no HTML format, but there is an RTF format", plus `public.utf8-plain-text`, `NSStringPboardType` and UTF-16 types; another user names Notes' private type `com.apple.notes.richtext`. Apple's developer forum has the same type with no answer on its format (https://developer.apple.com/forums/thread/113322, 2019, read 2026-11-22). Maccy lists `com.apple.notes.richtext` among the types it knows (`p0deje/Maccy` `Maccy/Extensions/NSPasteboard.PasteboardType+Types.swift`). Whether current Notes (iOS 18-27, macOS 15-27) adds `public.html` on copy is UNVERIFIED; no source read here dumps it.
- **Notes' copy carries the highlight somewhere**, unlike its scripting paths: "Doing a copy & paste of highlighted text from Apple Notes to Bear preserves highlight colors" (user JLP, Bear community, 2026-01-16, https://community.bear.app/t/more-robust-import-from-apple-notes/18709). Which flavour carries it (RTF `\AppleHighlight`, an HTML background colour, or Notes' private type) is UNVERIFIED. Bear's own highlighter has five colours, green (default), red, blue, yellow, purple (https://bear.app/faq/the-multi-color-highlighter-tool/), so Bear must be mapping Notes' colours onto its own.
- **Plain paste of a Notes list into other apps** (user reports only): Apple Community thread 254680139 says a normal paste carries the "•" into the destination and Paste and Match Style brings an indent plus an asterisk (search snippet 2026-11-22; the page redirects to support.apple.com and could not be opened). UNVERIFIED beyond the snippet.
- Apple's Cocoa writer, by contrast, writes a `{hyphen}` `NSTextList` as `<ul class="ul2">` with `list-style-type: '—  '` and no `Apple-dash-list` class, and RTF marker `\{hyphen\}` with level text U+2043 `⁃` (local run, section 4). Apple's HTML reader ignores the class (section 4).

## 3. What each destination keeps from plain + RTF + HTML

### First: which flavour each engine reads (source code, read 2026-11-22)

Every destination asked about reads the pasteboard through WebKit, Chromium or a UIKit/AppKit text view, so the engine decides which of Cutling's three flavours is used.

| Engine | Reads, in order | Source |
|---|---|---|
| **WebKit on macOS** (Safari, Mac Mail's composer) | web archive → file names → **HTML** → RTFD → **RTF** → images → URL → plain | `apple-oss-distributions/WebKit` `Source/WebCore/platform/mac/PasteboardMac.mm`, `Pasteboard::read` (lines ~443-560), tag WebKit-7624.2.5.11.4 |
| **WebKit on iOS** (Safari, Mail's composer, every in-app web view, and Chrome on iOS outside the EU, where browsers must use WebKit). That Mail's composer pastes through this code: `PlatformPasteboardIOS.mm` line 261 special-cases image pastes when `IOSApplication::isMobileMail()` or `isMailCompositionService()` (bundle ids `com.apple.mobilemail`, `com.apple.MailCompositionService`, `Source/WTF/wtf/cocoa/RuntimeApplicationChecksCocoa.mm` lines 519-528); Mac Mail is `MacApplication::isAppleMail()` (`com.apple.mail`, line 455). | web archive → flat RTFD → **RTF** → **HTML** → images → URL → plain. The item's own fidelity order is respected only for drag and drop: `respectsUTIFidelities()` returns true only for the drag pasteboard, with the comment "FIXME: We should respect UTI fidelity for normal UIPasteboard-backed pasteboards as well." On Mac Catalyst, RTF and RTFD are not read at all. | `Source/WebCore/platform/ios/PasteboardIOS.mm`, `supportedWebContentPasteboardTypes` (line 453) and `respectsUTIFidelities` (line 400) |
| WebKit turning RTF into DOM (both platforms) | RTF → `NSAttributedString` → Apple's private `_htmlDocumentFragmentString:` with `style`, `u`, `s`, `strike`, `font` and others excluded "since we want style to be inline", so underline arrives as inline CSS, not `<u>`. Pasted HTML from another app is run through `sanitizeMarkup`. | `Source/WebCore/editing/cocoa/WebContentReaderCocoa.mm` lines 102-160, 662-760 |
| **Chromium on macOS** (Chrome, and Electron apps such as Slack desktop) | `text/html` given to the page = `public.html` if present, else **RTF converted to HTML** (`clipboard_util::GetHTMLFromRTFOnPasteboard`), else the plain string. The code comment: "Safari only places RTF on the pasteboard, never HTML. We can convert RTF to HTML". | `chromium/chromium` `ui/base/clipboard/clipboard_mac.mm`, `ReadHTML` lines 360-385 and 219-224 (last commit 2026-11-12) |
| Web editors (Quill, and most others) | DOM `paste` event: `text/html`, then `text/plain`; they never see RTF | `slab/quill` `packages/quill/src/modules/clipboard.ts` `onCapturePaste` lines 197-216 |
| AppKit `NSTextView` copy (for contrast) | writes RTF + plain only, no HTML | local run, section 2 |

What this means for Cutling (inference from the code above, not a device test):
- On **iOS**, Mail and any web page (Google Docs in Safari, Slack in Safari) build the paste from Cutling's **RTF**, not its HTML. The RTF must carry underline, highlight and lists by itself.
- On **macOS**, Mail, Safari, Chrome and Electron apps (Slack desktop) use Cutling's **HTML**. The HTML must carry them by itself.
- Both flavours have to be complete. Neither can be the "nice to have" one.

### How web composers read pasted HTML (library source, read 2026-11-22)

Slack's web/desktop composer and Google Docs are closed. Open editors that handle the same pastes show what HTML shapes survive:

| Editor | Underline | Highlight | Lists | Source |
|---|---|---|---|---|
| Quill (`slab/quill`) | `<u>` (Underline blot), or **inline** `style="text-decoration: underline"` (exact match) | inline `background-color` → its `background` format; `<mark>` has no Quill format | `ol, ul` → `matchList`; no dash type | `packages/quill/src/modules/clipboard.ts` lines 39-66, 541, 579-590. `matchStyles` reads `node.style`, i.e. **inline styles only**: a class rule in `<head>` such as Apple's `span.s1 {text-decoration: underline}` is not seen. |
| Lexical (`facebook/lexical`) | `<u>`, or inline `text-decoration` containing `underline` ("Google Docs uses span tags + text-decoration: underline") | **`<mark>` → `highlight`**; no mapping from `background-color` | `ol` → number, `ul` → bullet, plus check; no dash type | `packages/lexical/src/nodes/LexicalTextNode.ts` lines 1721-1793; `packages/lexical-list/src/LexicalListNode.ts` lines 73-82, 150-160 |
| Tiptap (`ueberdosis/tiptap`) | `<u>`, or any `text-decoration` containing `underline`; writes Markdown as `<u>…</u>` | **only `<mark>`**; colour from `data-color` or `background-color` when `multicolor` is on; a bare `<span style="background-color">` is not a highlight; writes Markdown as `==…==` | (separate extensions) | `packages/extension-underline/src/underline.ts` lines 47-70; `packages/extension-highlight/src/highlight.ts` lines 60-135 (last commit 2026-10-16) |

So the shapes most editors accept are `<u>` for underline (inline `text-decoration` as a second choice), `<mark>` for highlight (with an inline `background-color` on it for the colour), and plain `<ul>`/`<ol>`. Class-based CSS, which Apple's own HTML writer produces, is the shape most likely to be lost. Craft's team reports the same: some receivers drop `<head>` styles, so Craft "made all style inline" (https://www-staff.craft.do/blog/the-challenges-of-cross-app-copy-paste-and-our-solutions, 2024-05-15, read 2026-11-22). The same post says Slack and VS Code were "not recognizing HTML and RTF content correctly", Apple's HTML converter does not write standard nested lists, and Gmail on iOS "has troubles with nested NSTextLists".

### Per destination

**Apple Mail (Mac).** The composer is WebKit; on a Mac it reads Cutling's **HTML** first (engine table). Apple documents no list of what it keeps. WebKit renders `<u>`, `<mark>`, `background-color` and `<ul>`/`<ol>`, including a string `list-style-type` such as `'—  '`: WebKit's own Smart Lists write exactly that for dashed lists (`TextListParser.cpp`, section 2). That every one of these survives Mail's paste sanitizer is likely but UNVERIFIED by a device test.

**Apple Mail (iOS).** Same WebKit composer, but it reads Cutling's **RTF** before the HTML. Apple's guide: "tap the Text Format button above the keyboard … You can change the font style and color of text, use a bold or italic style, add a bulleted or numbered list, and more" (iPhone User Guide, "Send email", https://support.apple.com/guide/iphone/send-email-iph742b6abb1/ios, read 2026-11-22). The RTF becomes DOM through Apple's HTML writer (engine table). By the local run in section 4, that writer turns `\ul` into `text-decoration: underline`, Apple's highlight into a transparent `<mark>` plus a 15 % tinted span, `\cb` into `background-color`, and `{hyphen}` lists into `list-style-type: '—  '`. Whether the fragment variant WebKit uses (`_htmlDocumentFragmentString:`) writes the same as the full-document writer tested here is UNVERIFIED. A Gmail-for-iOS problem with nested `NSTextList`s is reported by Craft (above).

**Apple Notes (iOS and Mac) as a destination.**
- Apple's Mac guide: "While some formatting is retained when you paste, the original font and color may not be retained"; Edit > Paste and Retain Style keeps the original style; Paste and Match Style drops it (Notes User Guide, "Write and format notes on Mac", https://support.apple.com/guide/notes/write-and-format-notes-not9474646a9/4.9/mac/12.0, search snippet read 2026-11-22).
- Which flavour Notes reads on paste, and in what order, is not documented. Notes' own HTML reader (`ICNote(HTML) attributedStringFromHTMLString:`) recognises `<ul class="Apple-dash-list">` as Dashed (section 2), but that this reader is the paste path is UNVERIFIED.
- **Does a pasted background colour become a Notes highlight? Nothing read here settles it.** Against: on macOS 26.5.2, `background-color`, the `background` shorthand and `<mark>` written through AppleScript or Shortcuts were all stripped, and highlight is "UI-only" in Notes' App Intents (`eliotshea/notes-mcp` spike, §12 and §14). ## 4. Apple's highlight attributes (iOS 18 / macOS 15)

### From the SDK headers (Xcode SDKs iPhoneOS27.2 / MacOSX27.2, read 2026-11-22)

- `NSTextHighlightStyleAttributeName` (Swift `.textHighlightStyle`) is "a character-level NSAttributedStringKey for decorating a section of text highlighted for emphasis", available macOS 15, iOS 18, tvOS 18, watchOS 11, visionOS 2. Its only value is `NSTextHighlightStyleDefault`, commented "Supported only with TextKit2". Source: `UIKit.framework/Headers/NSAttributedString.h:46-47,85-87`; `AppKit.framework/Headers/NSAttributedString.h:47-48,86-88`.
- `NSTextHighlightColorSchemeAttributeName` (Swift `.textHighlightColorScheme`) picks the colour: `Default`, `Purple`, `Pink`, `Orange`, `Mint`, `Blue`. Default "is based on the tint/accent color for the rendering context. By default UIKit uses UIView.tintColor and AppKit uses NSColor.controlAccentColor." Same headers, lines 49-50 and 89-96.
- `UITextView.textHighlightAttributes` (iOS 18) and `NSTextView.textHighlightAttributes` (macOS 15) set how the Default scheme draws: `.foregroundColor` overrides the text colour and `.backgroundColor` the highlight colour; without a background colour it "is derived from NSForegroundColorAttributeName". UIKit's default is "a dictionary with tintColor for NSForegroundColorAttributeName". Source: `UIKit.framework/Headers/UITextView.h:306-307`, `AppKit.framework/Headers/NSTextView.h:583-584`.
- macOS has a responder action `-[NSTextView highlight:]` that toggles the attribute on the selection; "the sender should be a menu item with a representedObject of type NSTextHighlightColorScheme". `NSTextView.h:589-591`. No matching UIKit action turned up in `UITextView.h` (grep, 2026-11-22).
- No Swift `AttributedString` attribute scope for highlight exists in any `.swiftinterface` of the iOS 27.2 SDK (grep for `TextHighlightStyle` across `System/Library/Frameworks` and `usr/lib/swift`, 2026-11-22). The keys reach Swift only as `NSAttributedString.Key` bridged from the ObjC headers, so SwiftUI `Text(AttributedString)` should not draw them. UNVERIFIED by a render; inferred from the missing scope.
- Underline is the old `NSUnderlineStyleAttributeName` (`.underlineStyle`), an `NSUnderlineStyle` bit mask (single 0x01, thick 0x02, double 0x09, plus dot/dash patterns and by-word). `AppKit.framework/Headers/NSAttributedString.h:33,59-73`.
- Lists: `NSTextList` with marker formats `{disc}`, `{hyphen}`, `{decimal}` and others has been in UIKit since iOS 7 (`UIKit.framework/Headers/NSTextList.h:24-68`); `isOrdered` and the initialiser with `startingItemNumber` since iOS 16 (lines 107, 173); `includesTextListMarkers` ("whether TextKit includes text list markers in the contents", default false) since iOS 26 / macOS 26 (line 188).

### What Apple's own converters do with them (local run, macOS 27 SDK, "Cocoa HTML Writer" CocoaVersion 2775.1, 2026-11-22)

Test programs: `/private/tmp/claude-501/-Users-hafang-Repositories-Cutling/daaa096e-354b-49c1-a901-f74c458509f8/scratchpad/q4/export.swift` and `back.swift` (scratch, not in the repo). An attributed string with underline, a purple text highlight, a yellow `.backgroundColor`, and three `NSTextList` paragraphs (`{disc}`, `{hyphen}`, `{decimal}`) was written with `data(from:documentAttributes:)` and read back.

RTF written:
- Underline: `\ul under\ulnone`.
- Highlight: private Apple control words, printed exactly as `\AppleHighlight-1 \AppleHilightClrSch-1 hilite\AppleHighlight0 \AppleHilightClrSch0`. The scheme word's number is Purple `-1`, Pink `-2`, Orange `-3`, Mint `-4`, Blue `-5`; the Default scheme writes `\AppleHighlight-1` with no scheme word. (Note Apple's spelling "Hilight".)
- Background colour: `\cb2 bgcolor\cb1` against a colour-table entry.
- Lists: a full `\listtable` with `{\*\levelmarker \{disc\}}`, `\{hyphen\}` and `\{decimal\}`. The disc's level text is U+2022 `•`; the hyphen's is **U+2043 `⁃` (HYPHEN BULLET)**, not `-` or `–`; decimal is the number. Each paragraph carries `{\listtext	•	}`, `{\listtext	⁃	}`, `{\listtext	1	}` (tab, marker, tab).
- RTF read back restores `.underlineStyle`, `.textHighlightStyle` with `.textHighlightColorScheme`, `.backgroundColor`, and `NSTextList` with the same three marker formats. The `\listtext` marker text is dropped from the string on read.

HTML written:
- Underline: `span.s1 {text-decoration: underline}`.
- Highlight: `<mark style="background-color: rgba(0, 0, 0, 0.0)"><span class="s2">hilite</span></mark>` with `span.s2 {color: #9d33d6; background-color: rgba(157, 51, 214, 0.15)}`. The `<mark>` is made transparent; the colour is a 15 % tint of the scheme colour on a span, and the text itself is recoloured. Scheme colours written: Purple `#9d33d6`, Pink `#fb0d44`, Orange `#fd8208`, Mint `#1ff6e5`, Blue `#0a60ff`; Default took the accent colour (`#0a60ff` in a command-line process). For the Default scheme the writer mis-nests tags: `<span class="s1"><mark …>x</span></mark>`.
- Background colour: `span.s3 {background-color: #ffff0b}`.
- Lists: `<ul class="ul1">` with `ul.ul1 {list-style-type: disc}`; dashed is `<ul class="ul2">` with `ul.ul2 {list-style-type: '—  '}` (an **em dash** and two spaces); numbered is `<ol class="ol1">` with `list-style-type: decimal`.

HTML read back:
- `<u>`, `<ins>` and `style="text-decoration:underline"` all become `.underlineStyle = 1`.
- `<mark>` becomes `.backgroundColor` yellow (1, 1, 0), **not** `.textHighlightStyle`; `style="background-color:yellow"` gives the same. A highlight survives HTML only as a background colour; only RTF carries Apple's highlight attribute back.
- `<ul>` reads as `{disc}`, `<ol>` as `{decimal}`. `list-style-type:'—  '` and `'- '` come back as custom marker formats `"—  "` and `"- "`. `<ul class="Apple-dash-list">` without CSS reads as `{disc}`: Apple's HTML reader ignores that class name.
- Unlike RTF, the HTML reader puts the markers into the string: `"\t•\tdisc\n\t—  \tdashcss\n\t1\tone\n"`.

### Apple's docs and WWDC24

- Apple's documentation abstract for `NSAttributedString.Key.textHighlightStyle`: "An attribute that adds a highlight color to the text to emphasize it." (Foundation module, `c:@NSTextHighlightStyleAttributeName`). https://developer.apple.com/documentation/foundation/nsattributedstring/key/texthighlightstyle (JSON form read 2026-11-22).
- WWDC24 "What's new in UIKit" (session 10118, chapter "Text improvements" at 16:14): iOS 18's new text formatting panel "supports a new text highlight feature. It works by applying two new attributes. textHighlightStyle, for the range of text that should be highlighted, and textHighlightColorScheme, for the color used to render the highlight. There are 5 predefined color schemes, in addition to the default, which uses tint color." The panel is set by `UITextView.textFormattingConfiguration`, whose components include `.listStyles` and `.highlight`; setting it to nil opts out. https://developer.apple.com/videos/play/wwdc2024/10118/ (read 2026-11-22).
- The session says nothing about RTF or HTML export of the highlight. The local run above is the only evidence here: Apple's RTF writer carries it as `\AppleHighlight` / `\AppleHilightClrSch`, and its HTML writer turns it into a transparent `<mark>` around a tinted span, which reads back as a plain background colour.

### What Notes uses

- Notes' iOS 18 highlight offers exactly five colours, purple, pink, orange, mint and blue, with no custom colour; a highlight recolours the text as well as its background. MacRumors, https://www.macrumors.com/2024/06/11/ios-18-notes-app-colors/ (search snippet read 2026-11-22; no Apple Support page on Notes highlighting turned up).
- Notes' own storage: the forensic parser `threeplanetssoftware/apple_cloud_notes_parser` (last commit 2026-07-25) reads each text run's highlight from protobuf field `AttributeRun.emphasis_style = 14`, values 1 Purple, 2 Pink, 3 Orange, 4 Mint, 5 Blue (`proto/notestore.proto` lines 75-88, `lib/ProtoPatches.rb` lines 276-291; read via the GitHub API 2026-11-22). That is the same set and the same order as `NSTextHighlightColorScheme` and the RTF `\AppleHilightClrSch` numbers 1-5 above. So Notes' highlight maps onto Apple's `textHighlightColorScheme`. That Notes' text view uses the public attribute at runtime is likely but UNVERIFIED.
- The same parser shows Notes' list styles as distinct paragraph `style_type` values: `STYLE_TYPE_DOTTED_LIST = 100`, `STYLE_TYPE_DASHED_LIST = 101`, `STYLE_TYPE_NUMBERED_LIST = 102`, `STYLE_TYPE_CHECKBOX = 103`, with `indent_amount` for nesting and `underlined = 6` per run (`lib/AppleNote.rb` lines 40-50, `proto/notestore.proto`). The parser's own HTML export writes them as `<ul class="dotted">`, `<ul class="dashed">`, `<ol>` and `<ul class="checklist">` (`lib/ProtoPatches.rb` lines 374-386). That is the parser's choice, not what Notes puts on the pasteboard.

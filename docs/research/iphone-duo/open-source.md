# iPhone Duo in open-source apps, keyboards and Safari extensions

Fetched 2026-11-25. Every bullet: finding, link, licence of the repo, date of the change. Anything I did not read from a source is marked GUESS; anything I could not confirm is marked UNSURE. Raw saved code is in `code/` (each file starts with a header comment holding its permalink at a commit SHA and the licence); raw saved pages are in `sources/`. Nothing here is committed.

Licence rule I followed: I saved code raw only from repos with a licence that allows it (Apache-2.0, MIT). SYKeyboard has no licence, wBlock and Svadilfari are GPL-3.0, KeyboardKit is custom: I read those and saved no code from them. Copying GPL code into Monholt's apps would need a licence decision by the owner (GUESS: it would force GPL on the app).

## 1. Open-source keyboard extensions

- **divvun/giellakbd-ios (Apache-2.0, 61 stars, pushed 2026-11-24, not archived)** is the best working example. PR #290 "iOS 27 support and general fixes", merged 2026-11-18, merge commit `2104ba4c80b27b0b399db841cbfc7415f36d0fb6`: https://github.com/divvun/giellakbd-ios/pull/290
  - Size comes from the keyboard's own window scene, not `UIScreen.main`: `view?.window?.windowScene?.screen.bounds.size`, falling back to `UIScreen.main` until the view is in a window. Its comment says on devices with more than one built-in display `UIScreen.main` stays on one display while the keyboard can be on another. Saved: `code/divvun_giellakbd-ios--Keyboard-Models-DeviceContext.swift`.
  - Fold/unfold arrives with no rotation, so `viewDidLayoutSubviews` compares `lastScreenSize` with the current size and, if different and not mid-transition, schedules `applyScreenGeometryChange()` on the next main-queue turn (rebuilds theme, updates height constraint). Mid-transition updates are skipped because they leave a black box under the keyboard. Saved: `code/divvun_giellakbd-ios--Keyboard-Controllers-KeyboardViewController.swift` (at SHA below).
  - Globe key: shown whenever `needsInputModeSwitchKey` is true, no longer guessed from device model. `needsInputModeSwitchKey` is not reliable in `viewDidLoad`, so `viewWillAppear` rebuilds the layout if the value changed since it was built. This runs against Apple's DTS advice to check it in `viewDidLoad` (see section 4); giellakbd checks in both.
  - Banner view kept across rebuilds; `viewWillTransition` now calls `super`.
- **divvun/giellakbd-ios PR #291 "iPhone Duo keyboard heights"**, merged 2026-11-18, merge commit `05244eba21767839cafe5b8d61ccd38dd7ac14d3` (all saved code is at this SHA): https://github.com/divvun/giellakbd-ios/pull/291 (Apache-2.0)
  - Inner display detected by short side: 466 pt outer, 669 pt inner, threshold 600 pt (`duoInnerDisplayMinShortSide = 600`). Inner display keyboard height: 301 pt portrait, 267 pt landscape, "matches the system keyboard's key area plus our banner". Outer display uses the existing 5.4-inch table. Saved: `code/divvun_giellakbd-ios--Keyboard-Models-KeyboardHeightProvider.swift`, `code/divvun_giellakbd-ios--HostingAppTests-DuoKeyboardHeightTests.swift`, `code/divvun_giellakbd-ios--Keyboard-Models-SystemKeys.swift`.
  - The PR's own device checklist (all ticked, author says tested on iPhone Duo): fold and unfold with the keyboard open updates height and theme without a rotation; globe key shows and switches on both displays. This is the only open-source keyboard I found that reports a tested fold/unfold with the keyboard open. It reports no keyboard drop.
  - GUESS: the 301/267 numbers are the author's measure of the system keyboard on the simulator or device; the PR does not say which. Verify on Cutling's own screen.
- **getdictus/dictus-ios (MIT, 61 stars, pushed 2026-11-25)** audit issue #785, 2026-10-24: https://github.com/getdictus/dictus-ios/issues/785 and follow-up #982 (2026-11-19, open): https://github.com/getdictus/dictus-ios/issues/982
  - Same bug as giellakbd (the code is a vendored copy of Giella's): on the inner panel `UIScreen.main` stays on the cover panel (466x678 pt), so `isLandscape` is false even in inner landscape; measured `computeKbHeight grid=270.0 total=322.0 screen=466x678 landscape=false numberRow=true`. Proposed fix: read the keyboard's own window scene / trait collection.
  - DeviceKit 5.9.0 does not know `iPhone19,4`, so the keyboard falls back to 216 pt portrait / 175 pt landscape. (DeviceKit added the Duo in commit `b13a38e910af4e9a5650668cba6c4358784bba42`, PR #507, 2026-11-01, MIT: https://github.com/devicekit/DeviceKit/commit/b13a38e910af4e9a5650668cba6c4358784bba42.)
  - Once, the keyboard was blank on the cover panel right after choosing it from the globe menu (extension running, `keyboardFrame=466x216`); refocusing fixed it; not reproduced. Simulator only.
  - Quotes Apple's Xcode 27.1 release note: most app extensions cannot run in the Duo simulator runtime (187708767); yet this keyboard ran there. UNSURE which Xcode/runtime build the audit used.
  - Fold/unfold state: "State survives fold and unfold: ... open sheets" for the host app; the audit says nothing about the keyboard dropping.
- **SNMac/SYKeyboard (no licence file, so all rights reserved: read only; 0 stars; pushed 2026-11-10)**, Korean keyboard extension, issue #209, 2026-10-31, closed by PR #213: https://github.com/SNMac/SYKeyboard/issues/209
  - Names the risk list in a keyboard extension: height recomputed only in `viewWillAppear`, `viewWillTransition` and when the suggestion bar toggles, so a fold without a rotation may not update height; landscape fixed at 188 pt; one-handed width of 320 pt absolute.
  - Fix, commit `44e27babebf9f89163b592b9ab22c47ba3a9669f` (2026-10-31): https://github.com/SNMac/SYKeyboard/commit/44e27babebf9f89163b592b9ab22c47ba3a9669f . On the inner display the keyboard window is only the keyboard area (655x337), so judging orientation from window bounds always says landscape; the fix treats the (regular, regular) size-class pair as portrait height rules, like the system keyboard.
  - Issue #212 (2026-10-31) https://github.com/SNMac/SYKeyboard/issues/212 : measured safe-area values by hand on the simulator: Duo outer portrait 32 pt below the keyboard, outer landscape 16, inner portrait 70, inner landscape 16; Duo portrait leaves 7 pt each side. On outer-display landscape the keys drew flat because iOS reported a bottom safe area (66 or 18 pt) inside the keyboard view that the key area subtracted as margin; fix: key area ignores the bottom safe area. This reproduced on the `develop` branch too.
  - Lists the Apple forum reports as "Apple gave no answer": ReservedRegion and hinge API do not work in an extension (FB24979539, FB24883137); `needsInputModeSwitchKey` always false on 27.1 RC (FB25073949); the globe and dictation keys narrow or cover a custom keyboard on the outer display. These FB numbers are the author's text; FB24979539 differs from the FB24979367 in Apple thread 850917 (UNSURE which is right).
  - Issue #211 (open): the system keyboard splits into two halves around the fold in half-open posture on the inner display (spacebar too), and full-width when fully open; the author found no Apple guidance or API for a third-party keyboard to do this and left it out. https://github.com/SNMac/SYKeyboard/issues/211
- **KeyboardKit (KeyboardKit/KeyboardKit, custom "Other" licence, 1912 stars, pushed 2026-11-23)**: the library source is not in the public repo at the paths I could search (repo has `Package.swift`, `Demo`, `Docs`, binaries), so I could not read how it detects the Duo. What I read is Apple-side behaviour as described by its maker and its release notes.
  - Blog "iPhone Duo and KeyboardKit", 2026-09-20: https://keyboardkit.com/blog/2026/09/20/iphone-duo-and-keyboardkit . Native Duo keyboard observations: closed (outer display): the globe and dictation buttons are on the keyboard's bottom row (FaceID iPhones put them outside); half folded (inner display): the keyboard is split around the fold; fully open: normal landscape keyboard with globe and dictation outside the keys, rows slightly uneven. KeyboardKit before the work rendered the landscape configuration with smaller keys and no split.
  - Issue #1095 "Add support for iPhone Duo", 2026-09-26, closed: https://github.com/KeyboardKit/KeyboardKit/issues/1095 . Maintainer 2026-10-20: "This will be available in 11.1, including new layouts and styles, and a new split screen mode."
  - Release notes at commit `0517bb210644f1297d44fd280710319f7361b216` (saved `sources/KeyboardKit_RELEASE_NOTES_0517bb2.md`): 11.1.0 `Keyboard.DuoDetector` (later renamed `DeviceDetector`), `KeyboardContext.isDuoDevice`, `Keyboard.Placement` with split mode ("Small phone screens will however only support this in landscape orientation"); 11.1.3 "`KeyboardContext` automatically enables the input mode switcher on iPhone Duo" and "no longer adds bottom edge spacers on iPhone Duo, to match the real device"; 11.2.x emoji sizes `.iPhoneDuoOpen`, `.iPhoneDuoOpenLandscape`; 11.3.0 layout configuration "adjusted to match the native iPhone Duo open portrait". Release dates: 11.3.0 2026-11-21, 11.3.1 2026-11-22, 11.3.2 2026-11-23 (https://github.com/KeyboardKit/KeyboardKit/releases).
  - It forces the globe on for the Duo rather than trusting `needsInputModeSwitchKey` (consistent with the 849736 answer, and with the bug reported in 850917).

No keyboard extension in open source that reads `UIHingeInteraction` or reserved regions. ## 2. Open-source iOS apps (any category) and keyboards of the host

- **stablyai/orca (MIT, 136k stars)**, issue #36742, 2026-10-31, closed: https://github.com/stablyai/orca/issues/36742 . Unfolded Duo, iOS 27.2, tapping into a WKWebView text field crashed the app: `EXC_BAD_ACCESS` in `NSISEngine negativeErrorVarForBrokenConstraintWithMarker:errorVar:` reached from `UIKeyboardLayoutStar _updateSplitForDivisionRegions:`. Safari on the same device did not crash. Turning off the app's own probe stopped it. Fix PR #36948, merged 2026-11-01, commit `57e287b555c881f0245710fd54915c979e9c0468`: https://github.com/stablyai/orca/pull/36948 . What they changed: stopped constraining a follower view to `keyboardLayoutGuide` (read the keyboard end frame from `keyboardWillChangeFrame` instead) and removed the `UIHingeInteraction`. Their own text: "This crash is device-only, and we haven't reproduced it" in the simulator. Saved: `code/stablyai_orca--mobile-modules-orca-reserved-regions-ios-OrcaReservedRegionsModule.swift`.
- **get-bb/bb (MIT, 6002 stars)** issue #7549, 2026-11-14, open: https://github.com/get-bb/bb/issues/7549 . Same crash in a split-screen window on iOS 27.2, reproduced with a bare UIKit + WKWebView app. The reporter says deferring the keyboard's division-region update by one main-queue turn stops the crash on device; priming the keyboard with an off-screen `UITextField` (Orca PR #37260) and removing `keyboardLayoutGuide` tracking did not. A bot says NOT REPRODUCED, root cause unestablished. UNSURE whether any of this applies to a keyboard extension, because the crash is in the system keyboard, not a third-party one; relevance to Cutling is the host app's constraints, not Cutling's.
- **Automattic/pocket-casts-ios (MPL-2.0)** PR #5670, 2026-11-19, open: https://github.com/Automattic/pocket-casts-ios/pull/5670 . After going from open to half-open posture, an `inputAccessoryView` search bar ended up under the split keyboard: UIKit placed it right, then about 0.5 s later moved it down by the 34 pt bottom safe area. Workaround: note a posture change with `UIHingeInteraction`, then `reloadInputViews()` once the keyboard frame is stable for 0.2 s, at most three times. Simulator only (iOS 27.2). This is the one app that shows keyboard-frame instability after posture change.
- **mozilla-mobile/firefox-ios (MPL-2.0)** PR #36267, merged 2026-10-26, merge commit `2cb650d3a6faf5597cb01ff00b97fc259c36907c`: https://github.com/mozilla-mobile/firefox-ios/pull/36267 . "More keyboard state handling was needed, using `intersectionHeightForView` is more robust since the keyboard state may exist even if the keyboard is not showing." Use the keyboard frame's intersection with the view, not a stored "keyboard is shown" flag.
- **erkamyaman/capacitor-foldable (MIT)** issue #6, 2026-09-20: https://github.com/erkamyaman/capacitor-foldable/issues/6 . The Duo fires keyboard-will-show and keyboard-did-show on every fold with no text field focused, so Ionic hides its tab bar and caches the window height from the first keyboard open. Do not treat keyboard notifications as proof that a field has focus.
- **flutter/flutter (BSD-3-Clause)** issue #193096, 2026-09-21, open: https://github.com/flutter/flutter/issues/193096 . Keyboard dismissed when switching from open to flip posture; not dismissed-by-app. Matches Apple thread 850917.
- **eunsoogi/orot (no licence, 0 stars)** issue #839, 2026-11-14: https://github.com/eunsoogi/orot/issues/839 . Opening the keyboard reduces the window height and a navigation rail flips to bottom tabs; lesson: keep window placement separate from transient keyboard occlusion, do not subtract keyboard height from the layout class. Read only.
- **nuphos/nuphos (NOASSERTION)** PR #5042, merged 2026-11-24, `1a89cf532364c080a30b55ab326dfb2f69f736a6`: https://github.com/nuphos/nuphos/pull/5042 . Composer pinned to the keyboard by its bottom edge with a fixed height, so UIKit moves it inside the keyboard's own animation; not Duo specific but verified on iOS 27.2.
- **Black bars and orientation locks**: ChenYilong/CYLTabBarController (MIT) issue #719, 2026-11-03: https://github.com/ChenYilong/CYLTabBarController/issues/719 . The maintainer's answer (reply 2026-11-03, commit `dcbc3a2a99a20b541b2e23895293928935567192`, PR #720): an app that declares only Portrait is shown as a portrait window in the middle of the unfolded screen with black sides; to fill the inner display three things are needed: a real launch screen (`UILaunchScreen` or a dedicated launch storyboard, no custom classes), Landscape Left and Right declared in `Info.plist`, and runtime orientation masks that allow landscape on a foldable. For a phone that stays portrait, keep landscape in `Info.plist`, return portrait by default and open landscape after a hinge is detected (via `UIHingeInteraction`). I did not run this; the answer is a project's own claim. This conflicts with SYKeyboard's note that the inner display ignores the app's supported orientations (UNSURE which holds for an iOS 27.1 SDK build).
- **Safari-style web views**: yetanotherbrowser/yab (Apache-2.0) issue #989, 2026-11-19: https://github.com/yetanotherbrowser/yab/issues/989 . Pages run under the folded Duo's status column, so a site's top-right controls cannot be tapped (a tap hits Control Center). Proposed: lay the page out inside the safe area and fill the column with `WKWebView.underPageBackgroundColor`. mozilla-mobile/firefox-ios PR #36801 (open, 2026-11-24) https://github.com/mozilla-mobile/firefox-ios/pull/36801 : iOS 27.3 WebKit covers the horizontal obscured inset with its own system-background colour view; Firefox covers it with a view filled with `underPageBackgroundColor`, above WebKit's.
- **Other Duo adoption PRs read only by title/summary, not by diff** (UNSURE what they changed beyond the title): livinglist/Hacki #956 (GPL-3.0, window-width split view, state kept across resize/fold, background painted behind asymmetric status areas) https://github.com/Livinglist/Hacki/pull/956 ; slopus/happy #2069/#2070 (sidebar edge on the crease); Expensify/App #107546, #107605, #107926; bitchat #1792; Mattermost #10362; Tsurukame #978.

## 3. Open-source Safari web extensions

- **0xCUB3/wBlock (GPL-3.0, 3267 stars, pushed 2026-11-25)** issue #1105 "On Duo unfold screen the safari plugin can't be opened", 2026-11-10, closed same day: https://github.com/0xCUB3/wBlock/issues/1105 . Maintainer answer (verbatim, short): "On the unfolded Duo Safari opens the popup as a popover that starts out header-tall. The old popup pinned its height to that and got stuck there. It sizes from its content now and the whole thing shows up." Fixed in wBlock 4.0 (TestFlight on 2026-11-10). I did not find the fix commit: no commit on 2026-11-10 before 19:50 UTC matched, so it is probably on another branch (GUESS). **This is the only reported Duo problem with a Safari extension popup.** Rule: never pin a popup's height to its first measured height; the popover can start small on the inner screen.
- wBlock issue #850, 2026-09-19 to 2026-10-25: https://github.com/0xCUB3/wBlock/issues/850 . A build with Xcode 27.0 ran in compatibility mode on a real Duo (3.2.1); commit `334e2160` switched releases to Xcode 27.1 (iOS 27.1 SDK) and the app fills the screen with toolbar and tabs in the side column; commit `4cf93fb250` (2026-10-25) stops info sheets scrolling behind their headers (https://github.com/0xCUB3/wBlock/commit/4cf93fb250). ## 4. Apple forums and docs (word for word in `sources/`)

- **Thread 850917 "iPhone Duo - Current SDK State"** https://developer.apple.com/forums/thread/850917 , created 2026-10-13, saved `sources/apple_forum_850917.txt`. Reports for a keyboard extension: hinge detection not working, reserved area detection not working, `needsInputModeSwitchKey` false although iOS shows no globe, and closed to fully open loses focus (regression since Beta 1; the same happens with the native keyboard in Safari). Apple's DTS engineer (Albert, WWDR), verbatim: "Instead of looking for a specific "hinge" API, the system reports the physical hinge and reserved areas, like rounded corners or a camera housing, through safeAreas. If your keyboard spans both screens, the hinge acts as an "unsafe" area in the middle of your view." And: "you should check this property in viewDidLoad". And: "The regression where the text field loses focus and the keyboard dismisses usually happens if the extension crashes, takes too long to layout, or manually resigns first responder during a bounds change. The key to keeping the keyboard alive rather than tearing down and rebuilding your views." Later reply, verbatim: "I will review each item to confirm whether it constitutes a bug and assess the current status specifically, whether a workaround is available or a resolution has already been implemented." The thread ends 2026-10-15 with no confirmed fix. Feedback numbers named by the reporter: FB25073949, FB24883137, FB24979367, FB24785360. Thread page showed 8 posts; I read all but the full text of later OP replies (about FB13954760, a 2024 keyboard bug that Apple said is unrelated).
- **Thread 849736 "globe button appeared in RC 1"** https://developer.apple.com/forums/thread/849736 (already in Cutling's docs): Ziqiao Chen: iPhone Duo returns `needsInputModeSwitchKey` true and the custom keyboard must draw the globe or face App Review rejection. Saved `sources/apple_forum_849736.txt`. CONFLICT: 850917 and SYKeyboard report it returns false on 27.1 RC (FB25073949). Giellakbd's PR and KeyboardKit 11.1.3 both guard against this.
- **Thread 847644 group lab summary**, 2026-09-23, DTS: https://developer.apple.com/forums/thread/847644 . Fold or unfold "do not get a completely new scene ... the app undergoes a dynamic resizing", "iPhone Duo honors UIRequiresFullScreen and apps adapt in place", and for keyboards use `keyboardWillChangeFrameNotification` etc. Saved `sources/apple_forum_847644_group_lab.txt`. Nothing in it covers keyboard extensions.
- **Thread 848203 "iPhone Duo and the Safe-Area"**, accepted answer: query `proxy.reservedRegions(kind: .occlusion)` instead of testing for the device; the camera region is always present on the Duo. https://developer.apple.com/forums/thread/848203 . Saved `sources/apple_forum_848203_safe_area.txt`. The WWDC session named is "Strike a pose with adaptive layouts on iPhone Duo" (not fetched).
- **Apple page "Prepare your app for iPhone Duo"** https://developer.apple.com/iphone-duo/prepare/ , fetched 2026-11-25: SDK matrix (26 SDK = centred window with space around; 27 SDK = resizes, avoids status bar on the right; 27.1 SDK = full display, toolbars and tab bars vertical), and the lists: replace `UIScreen.main`, re-read size in `viewDidLayoutSubviews`/`viewWillTransition`, no layout by orientation, idiom or "regular width means iPad". Saved `sources/apple_iphone-duo_prepare.txt`. It says nothing about app extensions.
- **SDK headers on this Mac (iOS 27.2)**: `UIKit/UIHinge.h` and `UIHingeInteraction.h` mark `UIHinge`, `UIHingeStatus` (unknown, closed, partiallyOpen, fullyOpen) and `UIHingeInteraction` as `API_AVAILABLE(ios(27.1))`; angle is in radians. Path: `$(xcrun --sdk iphoneos --show-sdk-path)/System/Library/Frameworks/UIKit.framework/Headers/UIHinge.h`. Read in the headers (iOS 27.2 SDK): neither `UIHinge.h`, `UIHingeInteraction.h` nor `UIView.h`'s `reservedRegionsOfKind:options:` (also `ios(27.1)`) carries `NS_EXTENSION_UNAVAILABLE`, so the headers do not forbid them in an extension; the forum reports say they report nothing there. The headers say nothing about how a keyboard extension's view is hosted.
- Forum thread 851106 (https://developer.apple.com/forums/thread/851106, 2026-10-14) restates, from Apple's news post of 2026-10-05, that from April 2027 uploads need the iOS 27 SDK and the Duo screenshots; the poster asked Apple to confirm; one reply from the poster only, no Apple answer. UNSURE.

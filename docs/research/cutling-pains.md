## Q1. Placeholder syntax and features, per vendor

### TextExpander (Mac, Windows, Chrome; iOS see Q2)

All read 2026-11-20.

- Five fill-in types today: single-line field, multi-line field, date picker, popup menu, optional section. On expansion "a temporary Fill-in window will pop up before the Snippet is expanded"; the user fills every field, clicks OK, then the snippet expands. Fields with the same name are filled once and repeat everywhere. A "Show at Top" option lists all fields at the top of that window. Source: https://textexpander.com/learn/using/snippets/snippet-fill-ins (last updated 2026-10-06, read in Chrome).
- Plain-text fill-in tokens (used in script snippets; the editor shows them as visual blocks): `%filltext:name=quantity:default=1:width=4%` (single line, default width 20); `%fillarea:name=..:default=..:width=40:height=4%` (multi-line); `%fillpopup:name=ship timeframe:today:default=tomorrow:next week%` (popup, first value is the default unless one is marked `default=`); `%fillpart:name=Payment Due:default=yes%...%fillpartend%` (optional section, may contain other fill-ins); `%filltop%` (show at top). Names and defaults cannot contain `%` or `:` in this form. Source: https://textexpander.com/learn/using/snippets/snippet-fill-ins/advanced-fill-in-syntax
- Special codes: `%|` places the cursor after expansion; `%clipboard` inserts clipboard text; `%|...%\` selects a range; `%%` is a literal percent; `%Snippet:<abbreviation>%` nests a snippet. These are listed under "Mac / Windows / Chrome / iOS". Cursor-move keys `%>` `%<` `%^` `%v` and delimiter codes `%+` `%-` are listed for Mac/Windows/Chrome only, not iOS. Source: https://textexpander.com/learn/using/snippets/advanced-snippet-elements/special-codes
- Date and time macros are strftime-style: `%Y` `%y` `%B` `%m` `%d` `%e` `%H` `%I` `%M` `%p`, with `%1I` for an unpadded hour; examples `%e %B %Y` = "26 August 2021", `%m/%d/%y`. Since TextExpander 3.1 it also takes ICU/Unicode patterns as `%date:<pattern>%`, e.g. `%date:ww%`, `%date:QQQyyyy%`, `%date:h:mm:ss a' 'VV%`. On macOS month and day names follow Language & Region; another language needs a shell script with `LANG=de_DE.UTF-8`, and date math macros do not work inside shell-script snippets. Source: https://textexpander.com/learn/using/snippets/advanced-snippet-elements/advanced-date-time
- Date math is a macro placed before the date macros it shifts, and it shifts every date macro after it in the snippet (nested snippets too) until a "Reset Adjustment" macro. Editor: Math > Add Day(s) / Subtract. Source: https://textexpander.com/learn/using/snippets/advanced-snippet-elements/date-time (last updated 2021-12-17, read in Chrome). Plain-text form `%@+1D%Y-%m-%d` (tomorrow), `%@-1D...` (yesterday): https://www.engadget.com/2013-01-21-mac-productivity-ten-textexpander-date-snippets.html (2013 article).

### Espanso (Mac, Windows, Linux; no iOS app)

Source read at commit `80d9e353` on branch `dev` of github.com/espanso/espanso (GPL-3.0, pushed 2026-11-15), and espanso.org docs, all 2026-11-20. Permalinks use `https://github.com/espanso/espanso/blob/80d9e353e3c0a58c77feb72671cec4a61958366f/` as `<E>`.

- Variables are `{{name}}` in `replace`, declared under `vars:` with a `type` (date, clipboard, choice, form, shell, random...) and `params`. Renderer regex `\{\{\s*((?P<name>\w+)(\.(?P<subname>(\w+)))?)\s*\}\}`, so `{{form1.name}}` reads a sub-value: `<E>espanso-render/src/renderer/mod.rs#L36-L37`.
- Date extension: `params.format` is a chrono strftime string (docs link https://docs.rs/chrono/latest/chrono/format/strftime/index.html); `offset` is a signed number of seconds (`86400` = tomorrow, `-86400` = yesterday), so date math is seconds only, no "+1 month"; `locale` is BCP47 (e.g. `en-US`) and defaults to the system locale; `tz` takes an IANA name (v2.3.0+) and an invalid one falls back to local time; with no `format` the output is RFC 2822. Code: offset parsed as `i64` seconds `<E>espanso-render/src/extension/date.rs#L59-L72`; locale defaults to `locale_provider.get_system_locale()` `<E>espanso-render/src/extension/date.rs#L77-L81`; rendering is `date.format_localized(format, locale)` and an unknown locale string silently becomes `Locale::en_US` `<E>espanso-render/src/extension/date.rs#L132-L150`. Docs: https://espanso.org/docs/matches/extensions/ (date examples use `%H:%M` and `%x`).
- Forms: a match with `form:` instead of `replace:` holds `[[field]]` controls, e.g. `form: "Hey [[name]],\nHappy Birthday!"`. `form_fields` sets per-field `type` (default text; `multiline: true`, `default`), `type: choice` (dropdown, `values` array or multiline string), `type: list` (list box, multi-select from v2.4.0, joined with ", " or a `separator`). Submit by clicking Submit or Ctrl+Enter; on macOS Tab moves between text fields. Fields are 100 px wide and grow; `max_form_width`/`max_form_height` from v2.2.2. Source: https://espanso.org/docs/matches/forms/
- Form parsing in code: the loader rewrites each `[[name]]` to `{{form1.name}}` and passes the original text as the form's `layout`; `\{` `\}` escape literal braces. Regex `\[\[\s*(\w+)(\.\w+)?\s*\]\]` `<E>espanso-config/src/matches/group/loader/yaml/mod.rs#L48-L49`, rewrite `<E>espanso-config/src/matches/group/loader/yaml/mod.rs#L242-L298`. The form window parses the layout line by line into text and field tokens, accepting both `[[name]]` and the legacy `{{name}}` (changed in v2.1.0-alpha) `<E>espanso-modulo/src/form/parser/layout.rs#L24-L73`. Field types `text` / `choice` / `list`, anything else panics: `<E>espanso-modulo/src/form/config.rs#L114-L153`. The form extension returns a map of field name to value, or Aborted: `<E>espanso-render/src/extension/form.rs#L54-L77`.
- So Espanso's form window shows the snippet's own text with the fields inline in it (layout = the snippet text), not a separate list of labelled fields. Read from layout.rs (rows of Text and Field tokens) and the docs' `Hey [[name]], Happy Birthday!` example.
- Choice extension (v2.1.2+): `type: choice` with `values` opens the search bar with the values as options; values may be a list or `label`/`id` pairs. `<E>espanso-render/src/extension/choice.rs` and https://espanso.org/docs/matches/extensions/
- Clipboard: `type: clipboard` variable, e.g. `replace: "<a href='{{clipb}}' />$|$</a>"`. Source: https://espanso.org/docs/matches/extensions/
- Cursor: `$|$` in `replace`, one per match (more are ignored); placed by simulating left-arrow presses, so auto-indenting editors can put the cursor in the wrong place; works well in single-line replacements. Source: https://espanso.org/docs/matches/basics/

### Raycast (Mac, Windows; iOS app since 2025)

All read 2026-11-20.

- Placeholders are words in braces: `{clipboard}`, `{snippet name="..."}`, `{cursor}` (Snippets only, one per snippet), `{date}`, `{time}`, `{datetime}`, `{day}` (weekday name), `{uuid}`, `{selection}`, `{argument}`, `{calculator}`, `{browser-tab}`. Parameters `offset=`, `format=`, `locale=`, `name=`, `default=`, `options=`; modifiers piped with `|`: `uppercase`, `lowercase`, `trim`, `percent-encode`, `json-stringify`, `raw`, chainable as `{clipboard | trim | uppercase}`. Source: https://manual.raycast.com/dynamic-placeholders
- Dates: with no `format`, output follows the system date and time preferences. `format=` takes Unicode (ICU) patterns, case-sensitive: `{date format="yyyy-MM-dd"}`, `{date format="MM/dd/yyyy"}`, `{date format="h:mm 'on the eve of' MMMM d"}`; `format` cannot be combined with `locale`. `locale="fr-FR"` (hyphen, not underscore; an unknown one makes the placeholder invalid). Offsets are sign + number + unit with `m` minutes, `h` hours, `d` days, `M` months, `y` years, several allowed: `{date offset="+2y +5M"}`, `{time offset="+3h +30m"}`, `{day offset=-3d}`; `"+ 2d"` is invalid. Source: https://manual.raycast.com/dynamic-placeholders and https://manual.raycast.com/dynamic-placeholders.md
- The Snippets manual page itself shows a different form, `{date: YYYY-MM-DD}`, and says "A typo in the placeholder name will cause it to be inserted as plain text." Source: https://manual.raycast.com/snippets.md. The two Raycast pages disagree on date syntax; the dedicated placeholders page is the detailed one.
- `{argument}`: each one adds an input field in Raycast's search bar, up to 3 distinct arguments; same `name` = one value; `default=` makes it optional, otherwise the command cannot run until it is filled; `options="happy, sad, professional"` gives a fixed choice list. Source: https://manual.raycast.com/dynamic-placeholders. Arguments came to snippets in v1.66.0 (2024-01-24), "to tweak part of a snippet just before expanding it": https://www.raycast.com/changelog/1-66-0
- `{clipboard offset=1}` reads the second most recent clipboard entry (needs Clipboard History); `{clipboard}` is removed when nothing was copied recently. Source: https://manual.raycast.com/dynamic-placeholders.md
- Keyword expansion modes: Immediately, After Delimiter (keeping), After Delimiter (discarding). Source: https://manual.raycast.com/snippets.md

### Alfred (Mac)

All read 2026-11-20.

- Placeholders in curly brackets: `{date}`, `{time}`, `{datetime}` with optional format names `short` / `medium` / `long` / `full` after a colon; no format = macOS's medium format, following System Settings > Language & Region. Examples: `{date}` = "28 Feb 2010", `{date:short}` = "28/02/2010", `{datetime:long}`. Source: https://www.alfredapp.com/help/workflows/advanced/placeholders/ (read in Chrome)
- Date arithmetic inside the placeholder, before the colon: `+`/`-`, number, unit `Y` `M` (strict uppercase) `D` `h` `m` (strict lowercase) `s`. Examples: `{date +1D}`, `{time -3h -20m}`, `{date +7d +3h:long}`, `{datetime -1Y:yy}`. Same source.
- Custom formats are Unicode (ICU) patterns after the colon: `{date:EEEE}`, `{date:MMMM yyyy}`, `{date +1M:MMMM}` (localised). `isodate`, `isotime`, `isodatetime` are fixed to the `en_US_POSIX` locale for predictable output, e.g. `{isodate -7d:dd/MM/yy}`, `{isodate:E, dd MMM yyyy HH:mm:ss Z}`; Alfred advises the iso forms unless localised names are needed, citing Apple's QA1480. Same source.
- `{clipboard}` = latest clipboard entry as plain text; `{clipboard:1}`, `{clipboard:2}` reach older items (needs Clipboard History). `{cursor}` sets the caret after pasting. `{random:UUID}`, `{random:1..5}`, `{random:cheese,apple,biscuits}`. `{snippet:!sig}` embeds a snippet (not recursively). Modifiers after a dot: `{clipboard.trim.stripdiacritics}`, `uppercase`, `lowercase`, `capitals`, `reverse`, `stripnonalphanumeric`. Same source.
- Snippets have no built-in fill-in field. The documented route is a workflow: a Snippet Trigger (typing e.g. `\\hellomsg` in any text field) opens Alfred's window on a Keyword Input set to "Argument Required"; the typed value goes into `{query}` of a Copy to Clipboard output that pastes into the frontmost app. A List Filter in place of the Keyword Input gives preset choices. Source: https://www.alfredapp.com/help/workflows/triggers/snippet/snippet-triggers-with-dynamic-inputs/ (WebFetch). Search-result snippets of Alfred forum threads (topic 12497 "simple UI for ... advanced snippets", topic 19241 "multiple inputs form-like") say the feature is missing and multi-field forms are not possible; thread bodies UNREAD.

### Snippety (Mac + iPhone/iPad keyboard; the closest rival to Cutling's shape)

All read 2026-11-20. Help pages fetched with curl and stripped to text.

- One syntax for everything: `{@type|param|param@}`, parameters split by `|`. Examples: `{@text|First Name|John@}` (text variable with default), `{@text|First Name@}`, `{@selectable|Meeting Type|Standup;Sprint Planning;Retrospective@}` (values split by `;`, `\n` for multi-line values, optional default, optional Hidden flag), `{@calculated-date|-1m2d|dd.MM.yyyy|English@}`, `{@cursor@}` (once per snippet), `{@clipboard@}` / `{@clipboard|Upper Case@}`, conditional blocks `{@if|Plan == Premium@}...{@else@}...{@endif@}`. Same title + same parameters = one value reused everywhere. Sources: https://snippety.app/help/macos/placeholders/overview , .../text-variable , .../selectable-value , .../calculated-date , .../cursor , .../clipboard-content , and https://snippety.app (home page examples).
- Calculated date: offset units `d`, `m` (months), `y`, combined freely, `-` to subtract (`1d-2m1y`); no hours or minutes in the date one (a separate Calculated Time placeholder exists). Format is an ICU/Unicode pattern, default `dd.MM.yyyy` (`yyyy-MM-dd`, `M/d/yyyy`, `E, d MMM yyyy`); a third parameter picks the language for month and weekday names, default English, not the system locale. Source: https://snippety.app/help/macos/placeholders/calculated-date
- Five placeholder families: smart (resolved automatically: date, time, counter, random), dynamic (need input: text, multiline text, selectable value, multiselect, selectable date), content (clipboard, selected text, file), reference, special (cursor, simulated keys, note). "When your snippet requires input, you will see a nice Live Template to fill in required values." Source: https://snippety.app/help/macos/placeholders/overview
- Mac Live Template: a form that appears automatically on expansion with a live preview of the snippet; Tab / Shift-Tab between placeholders, Ctrl-Tab to the next empty one, Space opens a picker, Enter confirms and expands; a simple form without preview is an option. Source: https://snippety.app/help/macos/using-snippets/live-template
- Mac Inline Placeholders (opt-in): fill text variables while typing the keyword, `:email<John<`, `<` between values and at the end, `:email<<` takes defaults, `:email.` forces the form; a list of the placeholders shows top-right while typing. Source: https://snippety.app/help/macos/using-snippets/inline-placeholders
- Mac cursor: Snippety cannot read the text field, so it counts the snippet's length after `{@cursor@}` and simulates that many left-arrow presses; some apps drop fast key presses or turn tabs into spaces and the cursor lands wrong; keep the cursor near the end of long snippets. Source: https://snippety.app/help/macos/creating-template/cursor-position
- iOS: `{@clipboard@}` inserts plain text only (no images) on iOS. Source: https://snippety.app/help/macos/placeholders/clipboard-content. The App Store listing (version 13.2.75, 2026-10-21, iOS 18.0+) says the Snippety Keyboard "supports QWERTY, QWERTZ, AZERTY, and Dvorak layouts, allowing you to search snippets and fill placeholders directly from the keyboard", and its NOTE says the keyboard types only "English letters + diacritics"; keyboard input "is used to fill placeholders, search, or expand snippets by keyword, and these features are limited to the English alphabet." Source: https://itunes.apple.com/lookup?id=1530751461&country=us (description field). So Snippety's iOS keyboard draws its own letter keyboard inside the extension to type fill-in values.
- Developer reply on the App Store (undated in the page text): "Now you can access your snippets from wherever you type using the new Snippety Keyboard! Also mobile app gets placeholders support now!" Source: https://apps.apple.com/us/app/id1530751461?see-all=reviews

### WordBoard (iPhone/iPad keyboard; the app whose buyer asked for "custom variables", row A7)

All read 2026-11-20.

- Variables in double braces with a quoted argument: `{{ date:"d MMM yyyy" }}` (ICU/Unicode pattern; WordBoard points users to NSDateFormatter.com), `{{ datehouroffset:"h:mm a", 2 }}` (shift in hours, half hours allowed, e.g. 5.5; negative goes back; `24` = tomorrow), `{{ clipboard }}`, `{{ selected }}`, `{{ cursor }}` (only the first one counts), `{{ randomize:"Thanks|Thank you|Cheers" }}`, `{{ choose:"soon|at the cafe|at the office" }}`. Names are case-insensitive and `=` may replace `:`. A language code after the format localises names: `{{ date:"EEEE", "de" }}` types "Mittwoch"; `datehouroffset` takes no language code. Blank clipboard/selection inserts nothing. Sources: https://support.bytesizeapps.net/article/19-how-do-i-use-templates-and-variables-in-wordboard and https://support.bytesizeapps.net/article/20-dynamic-dates-and-times-in-wordboard-variables
- There is no free-text fill-in. The only insert-time input is `choose`: "When you tap the key, a small menu appears next to it. Pick an option and WordBoard types the whole message with your choice in it." Several lists are asked in turn; the same list twice is asked once; an empty option shows as "(blank)"; Cancel types nothing. Same source (article 19).
- Release notes for 12.0.0 (2026-11-09): "Variables work in formatted keys, including Choose and Clipboard." Source: https://itunes.apple.com/lookup?id=960167417&country=us

### aText (Mac, Windows)

- The home page lists "date time scripts, editable field, key stroke" among its functions; the FAQ says the date/time format is changed by double-clicking a Date/Time variable in the snippet editor, so aText edits these as visual tokens and publishes no text syntax. It also offers "Automatically use Clipboard for long text" because typed-out long text goes wrong in web browser apps. No iOS app is named. Sources: https://www.trankynam.com/atext/ and https://www.trankynam.com/atext/doc/index.html (read 2026-11-20). Token syntax: UNREAD, not published.

## Q2. How shipped iOS snippet keyboards take fill-in values at insert time

The constraint: a custom keyboard is the input source, so a text field it shows cannot call up the system keyboard (see Q3). Every product below works around that in one of four ways: (a) ship a full letter keyboard and type the value with it, (b) offer only choices, no free text, (c) fill from values saved earlier in the app, (d) jump to the containing app. Read 2026-11-20 unless dated otherwise.

### TextExpander

- Retired keyboard (TextExpander 3 era, through at least April 2026): fill-ins did not work in the keyboard. Help page, as archived 2021-08-05: "Adding support for fill-ins using the keyboard is an obvious next step. We are working hard to implement this feature. Currently, on iPhone and iPad, fill-ins work in TextExpander 3's Notes or a TextExpander-enhanced app." Source: http://web.archive.org/web/20210805182536/https://textexpander.com/kb/ios/why-cant-fill-in-snippets-work-in-the-keyboard . The same text was still on the page on 2026-04-10: http://web.archive.org/web/20260410125051/https://textexpander.com/learn/using/introduction-to-textexpander-for-iphone-ipad/using-fill-ins-with-the-textexpander-keyboard ; the live URL now returns "Page not found".
- Earlier route (TextExpander touch 2.0, May 2013, date inferred from the article's image file names): in apps built with the TextExpander touch SDK, typing a fill-in abbreviation deleted it and jumped to the TextExpander app, which showed the fill-in window; Done returned to the host app with the text expanded. Built on x-callback-url; only Drafts supported it in the reviewer's testing. Source: https://www.macstories.net/reviews/textexpander-touch-2-0-brings-fill-in-snippets-formatted-text-to-ios/ (WebFetch).
- New app (id 6805960547, released 2026-09-02, v8.4.9, iOS 18+): a full typing keyboard with swipe, autocorrect, emoji search, one-handed mode, and "Fill-ins give superpowers to your TextExpander snippets, and they work in the app as well. Type the abbreviation, complete your fill-ins, and send." Source: https://apps.apple.com/us/app/textexpander/id6805960547 (lookup API description). Help: the keyboard lets you "Use fill-ins and complete the fields before the final text expands" (https://textexpander.com/learn/using/textexpander-for-iphone-ipad/how-to-set-up-textexpander-for-iphone-ipad , last updated 2026-09-04, read in Chrome) and "Use Fill-in and macros on your mobile device" (https://textexpander.com/learn/using/textexpander-for-iphone-ipad , same date). So TextExpander made fill-ins possible by becoming a full letter keyboard (route a). GUESS: the values are typed on the TextExpander keyboard's own keys into a field it draws; no page describes the fill-in screen.
- Reviews of the new app (RSS, most recent): "it interferes with dictation", "insists on making itself the default keyboard" (2026-10-06), Magic Keyboard malfunction on iPadOS 27.0.1 (2026-10-15), no way to edit or add snippets in the app (2026-09-15, 2026-09-29). Source: https://itunes.apple.com/us/rss/customerreviews/id=6805960547/sortBy=mostRecent/json . None mention fill-ins.

### Snippety

- The keyboard has its own QWERTY/QWERTZ/AZERTY/Dvorak letter keys used "to search snippets and fill placeholders directly from the keyboard", limited to "English letters + diacritics" (route a, cut down to one alphabet). Source: App Store description, https://itunes.apple.com/lookup?id=1530751461&country=us (v13.2.75, 2026-10-21). See Q1 for its syntax and the Mac Live Template form.

### Raycast for iOS

- The Raycast Keyboard is "a full typing keyboard for iPhone and iPad" in English plus downloadable Spanish, French, Italian, Portuguese, Dutch, Danish, German and Swedish. "If the Snippet has arguments, the keyboard asks for them first, and a `{cursor}` placeholder places the cursor in the expanded text." Quicklinks with `{argument}` likewise ask first. ### WordBoard

- No free-text fill-in; `{{ choose:"a|b|c" }}` shows "a small menu ... next to" the key, one list after another, then types the message (route b). Source: https://support.bytesizeapps.net/article/19-how-do-i-use-templates-and-variables-in-wordboard

### ClipKeyboard

- Template blanks are filled by picking values saved earlier, shown in the keyboard; a `+` to add a new value opens the containing app with `clipkeyboard://placeholder?token=...` (routes c and d). The source comment states the reason: in the in-app preview a value can be typed because the system keyboard can come up, but the real keyboard extension, being the keyboard itself, cannot call up keys to receive letters, so it tells the user to add the value in the app and come back. Source (Korean comment, translated here): https://github.com/M1zz/ClipKeyboard/blob/f29ec6d0292011b2ab87148255006edbce5d1168/ClipKeyboardExtension/KeyboardOverlays.swift#L121-L130 ; URL open: https://github.com/M1zz/ClipKeyboard/blob/f29ec6d0292011b2ab87148255006edbce5d1168/ClipKeyboardExtension/KeyboardViewController.swift#L211-L259 , which walks the responder chain to `UIApplication` or any responder answering `openURL:` (a private-API-shaped route; see guideline 4.4.1 in Q3). Repo has no licence: read, do not copy.
- ClipKeyboard has since also become "a full keyboard too, with iPhone-style keys in 23 languages" (App Store listing, v5.1.24, 2026-11-18), the same move TextExpander made.

Text Blaze and Magical: the App Store search for "Text Blaze" and "Magical" on 2026-11-20 returned no app from either vendor (itunes.apple.com/search), so neither ships an iOS keyboard that this research could find. Espanso has no iOS app (its repo builds Mac, Windows, Linux only; GUESS from the repo layout, not a stated policy).

## Q3. What iOS allows inside a keyboard extension

### A text field inside the keyboard

- Apple's custom keyboard guide lists what a keyboard cannot do (secure fields, phone pads, apps that opt out, text selection, editing menus, inline autocorrect UI, artwork above its top edge) and says nothing about text fields inside the keyboard's own view. Source: https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html (updated 2017-10-19, WebFetch 2026-11-20).
- What happens in practice (Stack Overflow, read through api.stackexchange.com 2026-11-20): a developer could focus a `UITextField` on top of the keyboard and type into it "using my custom keyboard", but `resignFirstResponder` did not hand input back to the host app, so the keyboard stopped typing anywhere (q 26173638, 2014-10-03; q 27935625, 2015-01-14, where an answer says Apple Technical Support called it "a bug of iOS keyboard extension" and the fix was a `UILabel` instead of a text field). An accepted workaround (q 34420344, answer 2015-12-24): disable user interaction on the field so it never becomes first responder, draw a fake blinking cursor, and route the keyboard's own key presses either to the field's `setText:` or to `textDocumentProxy.insertText` / `deleteBackward` depending on which is active. So no system keyboard ever appears for a field inside a keyboard; the keyboard must have its own keys to type into it. https://stackoverflow.com/q/26173638 , https://stackoverflow.com/q/27935625 , https://stackoverflow.com/q/34420344
- The same constraint written in a shipped product's source: ClipKeyboard's comment that the keyboard extension "cannot call up keys to receive letters" because it is the keyboard (Q2).

### KeyboardKit's way: route the keyboard's own keys into a field it owns

- KeyboardKit is closed source today: its LICENSE at HEAD (`fa34c404`, 2026-11-16) reads "Closed Source License ... KeyboardKit ... is closed-source", copyright Kankoda Sweden AB; the source must not be used by others. https://github.com/KeyboardKit/KeyboardKit/blob/fa34c40404496338162651b807f1203ab3ff7050/LICENSE . Its demo still shows `KeyboardTextField(text: $text, context: context)` focused inside a toolbar "to demo how users can type text within the keyboard": https://github.com/KeyboardKit/KeyboardKit/blob/fa34c40404496338162651b807f1203ab3ff7050/Demo/Keyboard/DemoTextInputToolbar.swift#L12-L48
- Up to the 8.x line it was MIT (tag 7.9.8, commit `bc8949cd`, "MIT License, Copyright (c) 2021 Daniel Saidi"), and the mechanism is readable there:
  - `KeyboardInputViewController` overrides `textDocumentProxy` to return `textInputProxy ?? mainTextDocumentProxy`, where `mainTextDocumentProxy` is `super.textDocumentProxy`: https://github.com/KeyboardKit/KeyboardKit/blob/bc8949cd12d591c6b9eb45e66b9b49d9959c0024/Sources/KeyboardKit/KeyboardInputViewController.swift#L190-L219
  - When a `KeyboardTextField` / `KeyboardTextView` becomes first responder it sets `controller.textInputProxy = TextInputProxy(input: self)`; on resign it sets it back to nil; a typed "\n" resigns when `resignOnReturn` is true: https://github.com/KeyboardKit/KeyboardKit/blob/bc8949cd12d591c6b9eb45e66b9b49d9959c0024/Sources/KeyboardKit/Routing/KeyboardInputComponent.swift#L42-L76
  - `TextInputProxy` implements `UITextDocumentProxy` over any `UIResponder & UITextInput`: `insertText`, `deleteBackward`, `documentContextBefore/AfterInput` from the field's text ranges, and `adjustTextPosition` by moving `selectedTextRange`. Credited to a gist by @wearhere. https://github.com/KeyboardKit/KeyboardKit/blob/bc8949cd12d591c6b9eb45e66b9b49d9959c0024/Sources/KeyboardKit/Routing/TextInputProxy.swift#L15-L147
  - `KeyboardTextField` wraps a `UITextField` subclass (`KeyboardInputTextField`) that calls those hooks: https://github.com/KeyboardKit/KeyboardKit/blob/bc8949cd12d591c6b9eb45e66b9b49d9959c0024/Sources/KeyboardKit/Routing/KeyboardTextField.swift#L13-L177
  - So every key the keyboard draws keeps calling `textDocumentProxy.insertText`, and the proxy swap decides whether it lands in the host app or in the keyboard's own field. This needs the keyboard to draw letter keys. Cutling's keyboard today is a grid of cutlings, not letter keys (GUESS from the project description; not re-read for this file).

### App Review guideline 4.4.1 (keyboards)

- Keyboard extensions "must: Provide keyboard input functionality (such as typed characters); ... Provide a method for progressing to the next keyboard; Remain functional without full network access and without requiring full access; ..." and "must not: Launch other apps besides Settings; or Repurpose keyboard buttons for other behaviors". Source: https://developer.apple.com/app-store/review/guidelines/ (curl 2026-11-20). A keyboard that opens its own containing app to collect a fill-in value (TextExpander touch 2013's model, ClipKeyboard's `+`) runs against "Launch other apps besides Settings"; GUESS whether Review treats the containing app as "other".

### Cursor placement and reading back text in web fields (Safari, WKWebView, Gmail)

No Apple or WebKit page states that `adjustTextPosition(byCharacterOffset:)` fails in web fields, and no WebKit bug titled for it was found (Bugzilla REST quicksearch for "adjustTextPosition", "UITextDocumentProxy", "documentContextBeforeInput" returned nothing, 2026-11-20). What is on record:

- Units: "Swift represents strings as a collection of grapheme clusters, and that's what Apple's deleteBackward method uses to index. But Apple's adjustTextPosition method uses UTF-16 code units to index." Grammarly engineering blog, https://www.grammarly.com/blog/engineering/string-index-type-safety-in-swift/ (updated 2026-03-05). So a `{cursor}` offset must be counted in UTF-16 units, and one `deleteBackward` per grapheme. The same pitfall is in KeyboardKit issue #124 (2020-09-29 comment): https://github.com/KeyboardKit/KeyboardKit/issues/124
- Safari contenteditable: moving the caret with the keyboard can carry it outside the focused element, and the proxy then reads text from DOM elements outside it ("adjustTextPosition can literally affect the focus"), reproduced on MDN's contenteditable example. KeyboardKit issue #555, opened 2023-04-04, closed as a discussion, no fix: https://github.com/KeyboardKit/KeyboardKit/issues/555 . GUESS: a cursor jump back of N characters inside one field stays inside it; the reported escape happens when the caret is pushed past the field's start or end.
- WebKit bug 179602 "[iOS third party keyboard] Keyboard got wrong output when type fast with delete and insert", status NEW since 2017-11-13 (last change 2022-02-09): reproduced 100% in WKWebView text inputs including Safari, not in Notes or Messages. https://bugs.webkit.org/show_bug.cgi?id=179602 . Fast `deleteBackward` + `insertText` sequences, the pattern a fill-in that replaces typed text uses, are the risky case in web fields.
- The proxy's context is short and stale: `documentContextBeforeInput` gives "only ... the content closest to the text input cursor", typically up to the previous sentence or line; after inserting multi-line text it holds only the last line (KeyboardKit #584, 2023-05-23, maintainer reply: https://github.com/KeyboardKit/KeyboardKit/issues/584 ; #281, 2021: https://github.com/KeyboardKit/KeyboardKit/issues/281). In Gmail and the Mail app, after a paste it "returns nil until the pasted text is edited" (Apple Developer Forums thread 812642, Jan 2026, DTS asked for a sample, no answer: https://developer.apple.com/forums/thread/812642). After a paste in WhatsApp, Signal and Telegram it returns only the last two sentences (thread 772158, Jan 2025: https://developer.apple.com/forums/thread/772158). `textWillChange` / `textDidChange` do not fire for text changed outside the proxy, and the context only refreshes after a caret move (thread 45121, Apr 2016, confirmed Jul 2019 by KeyboardKit's author, who used a timer that nudges the caret: https://developer.apple.com/forums/thread/45121).
- What this means for a fill-in that lets the user type the value with another keyboard and reads it back from `documentContextBeforeInput` (the route the uncommitted `CutlingKeyboard/FillInPanel.swift` takes): the read works when the value and the text Cutling typed before it sit on the same line near the caret; it can come back nil or cut short in Gmail/Mail and after pastes. GUESS: when the keyboard reappears after a globe switch, iOS hands it a fresh proxy, so the context is current then; not verified on device.
- Multi-line `insertText` into web contenteditable: no source found that says it fails or works; UNREAD. Apple's guide's own sample sends `"\n"` through `insertText` for a newline. A forum thread (developer.apple.com/forums/thread/735187, body UNREAD, seen as a search snippet) reports that `"\r"` appended to a string did not trigger a web form's auto-submit while `"\r"` alone did. Cutling already types multi-line cutlings through `insertText` today (CutlingKeyboard/KeyboardViewController.swift line 463 in the working tree), so device testing in Gmail and Safari is the check.

### Opening the containing app from the keyboard

- `extensionContext?.open(_:)` fails in a keyboard; KeyboardKit ships a `UrlOpener` workaround its author says "can stop working at any time" because it works around a limit Apple imposes. Issue #597, 2023-06-05: https://github.com/KeyboardKit/KeyboardKit/issues/597 . Combined with 4.4.1 ("must not: Launch other apps besides Settings"), a jump to the Cutling app to type a fill-in value is fragile and a review risk.
- Side note, same day: KeyboardKit 11.3 plans a dictation engine that embeds a web view in the keyboard, after Raycast shipped dictation without a round-trip to the main app (issue #1119, closed 2026-11-20, https://github.com/KeyboardKit/KeyboardKit/issues/1119). Not needed for fill-ins.

## Q4. Mac: how the fill-in prompt appears before pasting

Read 2026-11-20.

- TextExpander: "a temporary Fill-in window will pop up before the Snippet is expanded"; it shows the snippet with its fields; OK expands; "Show at Top" moves all fields to the top of that window, and a ▶ at the bottom left reveals the full snippet. Same-named fields fill once. https://textexpander.com/learn/using/snippets/snippet-fill-ins
- Snippety: "Live Template", a form that "appears automatically when you expand a snippet that has placeholders" and shows a live preview of the snippet while you fill it; Tab / Shift-Tab, Ctrl-Tab to the next empty field, Space opens a picker, Enter expands; a plainer "simple form" without preview is an option. Opt-in inline filling while typing the keyword (`:email<John<`). https://snippety.app/help/macos/using-snippets/live-template , https://snippety.app/help/macos/using-snippets/inline-placeholders
- Espanso: a separate form window whose body is the snippet's own text with each `[[field]]` drawn as an input in place (layout parsed line by line into text and field tokens); dropdowns for `choice`, list boxes for `list`; Submit button or Ctrl+Enter; Tab between text fields on macOS. https://espanso.org/docs/matches/forms/ and https://github.com/espanso/espanso/blob/80d9e353e3c0a58c77feb72671cec4a61958366f/espanso-modulo/src/form/parser/layout.rs#L34-L73
- Raycast: no separate form. Each `{argument}` becomes an input field inside Raycast's own search bar (up to 3), next to the selected snippet or command; "Fill them in and press `Enter`". Required ones block Enter until filled (Windows v0.68, 2026-07-09: "Consistently ensured we don't allow submitting with incomplete args (Root Search, Snippets, Quicklinks, AI commands, etc)"). https://manual.raycast.com/llms-full.txt (line "Some commands accept arguments (up to 3)...") and https://manual.raycast.com/dynamic-placeholders ; https://www.raycast.com/changelog/windows/2 . For keyword expansion in another app, the Windows changelog v0.67 (2026-07-03) fixes "the empty argument view would reopen when pressing ESC during snippet expansion", so on Windows an argument view opens during keyword expansion. The Mac behaviour on keyword expansion is not documented: UNREAD; GUESS that it opens the same Raycast window with argument fields.
- Alfred: no fill-in in snippets; a workflow's Snippet Trigger opens Alfred's main window on a Keyword Input ("Argument Required"), the typed text goes into `{query}`, Enter pastes into the frontmost app. One field per step; multi-field forms are not built in. https://www.alfredapp.com/help/workflows/triggers/snippet/snippet-triggers-with-dynamic-inputs/
- Pattern across all five: the prompt appears before anything is pasted, in a window the expander owns, and the text is pasted once, complete. None types part of the text and then waits. GUESS: on the Mac, Cutling's ⌘⇧V picker panel can host the same prompt (fields under the chosen cutling, Enter pastes), since the panel already owns keyboard focus before it pastes.

## Q5. Date formatting: pattern style and locale

Read 2026-11-20.

| Product | Pattern style | Default with no format | Locale |
|---|---|---|---|
| Raycast | ICU / Unicode TR35 (`yyyy-MM-dd`), case-sensitive, quoted literals | "follows your system preferences" | system; `locale="fr-FR"` overrides; `format` and `locale` cannot be combined |
| Alfred | ICU / Unicode after `:` (`{date:EEEE}`), or named `short`/`medium`/`long`/`full` | macOS medium format | system; `isodate`/`isotime`/`isodatetime` fixed to `en_US_POSIX` |
| Espanso | strftime via Rust chrono (`%Y-%m-%d`, `%x`) | RFC 2822 string | system locale by default; `locale: en-US` overrides; unknown locale falls back to en_US silently |
| TextExpander | strftime-like `%Y %m %d %B %e %H %M %p` macros, plus ICU via `%date:<pattern>%` (since 3.1) | n/a (editor inserts blocks) | macOS Language & Region for names |
| Snippety | ICU (`dd.MM.yyyy`, `E, d MMM yyyy`) | `dd.MM.yyyy` | explicit language parameter, default English (not the system) |
| WordBoard | ICU via NSDateFormatter (`{{ date:"EEEE, MMM d, yyyy" }}`) | needs a format | device; `{{ date:"EEEE", "de" }}` overrides |
| ClipKeyboard | ICU via `DateFormatter` | locale skeleton through `DateFormatter.dateFormat(fromTemplate:options:locale:)` | device |

Sources: https://manual.raycast.com/dynamic-placeholders.md ; https://www.alfredapp.com/help/workflows/advanced/placeholders/ ; Espanso `date.rs` permalinks in Q1 and https://docs.rs/chrono/latest/chrono/format/strftime/index.html (chrono 0.4.45: "`strftime`/`strptime`-inspired date and time formatting syntax", `%x` = "Locale's date representation"); TextExpander, Snippety, WordBoard, ClipKeyboard pages in Q1.

Apple's side (what Cutling's `DateFormatter` / `Date.FormatStyle` use):
- `DateFormatter` format strings "use the format patterns from the Unicode Technical Standard #35", version tied to the OS release; for fixed formats set the locale to `en_US_POSIX`, which yields the same output "regardless of both user and system preferences". https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/DataFormatting/Articles/dfDateFormatting10_4.html
- Apple: set `dateFormat` "only ... when working with fixed format representations"; for user-visible dates use `dateStyle` / `timeStyle` or `setLocalizedDateFormatFromTemplate(_:)`. https://developer.apple.com/documentation/foundation/dateformatter/dateformat (JSON at developer.apple.com/tutorials/data/documentation/foundation/dateformatter/dateformat.json)
- `DateFormatter.dateFormat(fromTemplate: "yMMMMd", options: 0, locale:)` gives "MMMM d, y" for en_US and "d MMMM y" for en_GB: a skeleton is localised, a raw pattern is not. https://developer.apple.com/documentation/foundation/dateformatter/dateformat(fromtemplate:options:locale:)
- So the Apple-native choice is ICU patterns (what Raycast, Alfred, Snippety and WordBoard expose), and a bare `{date}` should render with the user's own date style, as Raycast and Alfred do. GUESS for Cutling: a bare `{date}` uses the user's date style; a typed pattern is formatted in the user's locale so month and weekday names come out in their language, with `locale=` to override, as Raycast does. `en_US_POSIX` would keep numbers stable but turn every month name English.

Common ground: every product with a text syntax uses braces except TextExpander (`%`) and Espanso's `$|$` cursor. `{date}`, `{time}`, `{cursor}`, `{clipboard}` are spelled the same in Raycast, Alfred and ClipKeyboard, and WordBoard differs only by doubling the braces. ## Decisions this research supports

Inferences from the findings above, not read anywhere; each names the finding it rests on.

1. Token words: `{date}`, `{time}`, `{datetime}`, `{day}`, `{cursor}`, `{clipboard}` in single braces, because Raycast, Alfred and ClipKeyboard already spell them this way and WordBoard only doubles the braces (comparison table). A buyer moving from any of them retypes nothing.
2. Date math: sign, number, unit letter inside the token (`{date +3d}`, `{time -2h}`), case-sensitive `m` minutes / `M` months, as Raycast and Alfred do (Q1). Espanso's seconds-only offset and TextExpander's separate math macro are the outliers.
3. Date format: ICU patterns (`{date:yyyy-MM-dd}` Alfred-style, and Raycast's `format="..."` accepted too), rendered in the user's locale; a bare `{date}` uses the user's own date style; `locale=` overrides (Q5). Strftime `%Y` belongs to Espanso and TextExpander only.
4. Fill-in: a named blank whose same name repeats one value (TextExpander, Raycast, Snippety, WordBoard all do this, Q1). A bare `{Name}` matches Snippety's and ClipKeyboard's model but collides with literal braces in code and JSON cutlings; Raycast's answer is that an unknown word stays plain text, and Snippety avoids it with `{@...@}`. Whatever the spelling, an escape (`\{`) and a strict label rule are needed.
5. Choices: worth shipping alongside free text, because on iPhone a choice needs no typing at all (WordBoard's whole fill-in story is `choose`, Q2) and it covers the "swap a name" case from row A7 when the names are known.
6. One `{cursor}` per cutling, offsets counted in UTF-16 units, moved once backwards over text just inserted (Raycast, Espanso, Snippety, WordBoard all allow one; Grammarly on units; KeyboardKit #555 on Safari, Q3).
7. iPhone free-text value: every shipped keyboard that takes typed values draws its own letter keys (TextExpander 2026, Raycast, Snippety, ClipKeyboard), and Snippety's is English-only. Typing the value in the host field with the user's own keyboard, then returning (the uncommitted `FillInPanel.swift` route), is not done by any product found; it keeps every language, autocorrect and dictation, but depends on `documentContextBeforeInput`, which is nil after pastes in Gmail/Mail and short in chat apps (Q3). It needs a fallback that does not read the host: saved values and the clipboard as one-tap chips (ClipKeyboard), and a way to skip ahead.
8. Never jump to the Cutling app to collect a value from the keyboard: guideline 4.4.1 and KeyboardKit #597 (Q3).
9. Mac: prompt for all fields at once inside the ⌘⇧V panel before anything is pasted, Tab between fields, Enter pastes the finished text once; every Mac expander does it this way (Q4).
10. `{clipboard}` on iPhone: read the pasteboard only when the cutling holds the token, at insert time, and explain when Full Access is off (ClipKeyboard source, Q3 table).
11. Device checks still owed before shipping: multi-line `insertText` and `{cursor}` placement in Gmail compose in Safari and in the Gmail app; reading a typed value back after a globe-key switch in Mail, Gmail, WhatsApp and Safari (Q3, UNREAD items).

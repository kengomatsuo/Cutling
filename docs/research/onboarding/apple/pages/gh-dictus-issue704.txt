Onboarding: explain Full Access before the keyboard step
## Parent

#649 (onboarding rebuild for 2.0.0).

## Why

Testers have declined to set Dictus up because of Apple's Full Access alert ("the developer of this keyboard can transmit anything you type…"). They read it as something Dictus does, not knowing iOS shows the same text for every third-party keyboard that asks for it (Gboard, SwiftKey, Wispr Flow). Competitors do not explain it in their onboarding. We turn it into a point in Dictus' favour: say why it is needed before the user sees it, and that anyone can check what Dictus does with it because the code is open source.

## What to build

One short screen placed **right before** the keyboard step ("Activez le clavier"), in the #675 shell.

- Show Apple's alert ahead of time, drawn in code like the rest of the onboarding's system UI, so it is no surprise in Settings.
- Three points, one line of body each:
  1. **Why it is needed.** Without Full Access iOS does not let the keyboard dictate: the keyboard cannot use the microphone or reach the Dictus app, which transcribes. Without it, the keyboard types but cannot dictate.
  2. **What happens to the data.** Transcription runs on the iPhone; what you type and say stays on it.
  3. **Open source.** Anyone can read the code on GitHub and check. Link to `https://github.com/getdictus/dictus-ios`.

Draft FR copy (vous, no em dashes), to be finalised with EN:

> **Pourquoi l'accès complet ?**
> Apple affiche ce message pour tous les claviers qui ont un micro.
> • **Le micro en a besoin.** Sans accès complet, iOS interdit au clavier de dicter.
> • **Vos dictées restent sur votre iPhone.** La transcription se fait sur l'appareil, rien n'est envoyé.
> • **Vérifiable par tous.** Le code de Dictus est open source : n'importe qui peut le lire sur GitHub.

## Before the copy ships

Point 2 is a public promise. Verify it against the code the keyboard actually links and the app's App Privacy answers ("Data Not Collected"): a first pass found no network code in `DictusKeyboard`; `DictusCore`'s only `URLSession` is in `polish-harness`, a dev harness to confirm is not linked into the keyboard. Write the result on this issue. If any path sends data, the sentence changes, not the code.

**Category:** enhancement
**Summary:** One screen right before the keyboard step that tells the truth about Full Access: what it is, that it is all or nothing, what Dictus uses it for and what it does not use.

**Why (Pierre, 2026-10-12):** say the truth, and make the user understand why Dictus asks for it. Apple's alert reads as something Dictus does; it is the same text for every third-party keyboard that asks for Full Access.

**Facts the copy rests on (checked during triage):**
- **It is one switch, all or nothing.** A keyboard declares a single Boolean (`RequestsOpenAccess`); iOS offers no partial access. Without it, a keyboard has **no shared container with its own app** and no file system beyond its own container. With it, iOS also allows network access, Location Services and Contacts (with permission), iCloud through the app. Source: Apple's *App Extension Programming Guide*, Custom Keyboard, tables 8-1 and 8-2.
- **Apple shows the same alert for every keyboard that requests it**, with or without a microphone.
- **What Dictus uses it for:** reaching the Dictus app. The keyboard does not record: the app listens and transcribes, and the keyboard needs Full Access to hand over to it (opening the app, the shared App Group container for settings, transcripts and voice notes). Without it the keyboard types but cannot dictate.
- **What Dictus does not use:** no location and no contacts anywhere in the keyboard or DictusCore (no CoreLocation / Contacts import). Network: the only networking code in the shared core is the model download, which runs in the app and sends no user data. **This claim must be verified before merge** (see below).

## Network verification for the Full Access explainer copy

Checked on branch `feature/704-full-access-explainer`, from `develop` at d4b1fc14, on 2026-10-12. Goal: confirm the sentence *"vos dictées ne quittent pas votre iPhone : la transcription se fait sur l'appareil"* / *"your dictations never leave your iPhone: transcription happens on the device"*.

**Result: nothing in the keyboard's binary can make a network request. No path found in the keyboard or the app sends dictations or typed text off the device. The copy ships as the brief wrote it.**

### Measured

**What DictusKeyboard links** (`Dictus.xcodeproj/project.pbxproj`, target `AA500002`):
- `packageProductDependencies` holds two products: `DictusCore` (`AA900011`) and `DeviceKit` (`CC900001`). WhisperKit and FluidAudio are linked into DictusApp only (`AA900020`, `AA900030`).
- Its Sources phase (`AA600002`) compiles 57 files, all under `DictusKeyboard/`.
- The project has no file-system-synchronized groups, so no file reaches the target by implicit membership.

**DictusCore, as the keyboard links it:**
- `DictusCore/Package.swift` declares two products: the `DictusCore` library and the `polish-harness` executable.
- The pbxproj consumes only the library. The strings `polish-harness` and `PolishFidelity` appear nowhere in it.
- `URLSession`, `URLRequest`, `NWConnection` and `import Network` are searched under `DictusCore/Sources/DictusCore`. Only doc comments match: files about the download policy, which say the session itself lives in DictusApp.
- The package's one HTTP client is `Sources/polish-harness/LocalHTTPPolishEngine.swift`. It is throwaway #268 spike code that posts to a localhost OpenAI-compatible server, and it sits in the macOS-only executable target.
- No CoreLocation or Contacts import exists in `DictusKeyboard/` or `DictusCore/Sources/`.
- No analytics or crash SDK is imported anywhere (searched for Firebase, Sentry, TelemetryDeck, Mixpanel, Amplitude and RevenueCat).

**The built binary** (Debug simulator build of this branch):
- `nm -u` on `DictusKeyboard.appex/DictusKeyboard.debug.dylib` lists 2,048 undefined symbols. None matches `URLSession|NSURLConnection|nw_connection|CFSocket|CFStream|URLRequest|dataTask`.
- As a control, the same grep on `DictusApp.debug.dylib` returns 16 `URLSession` symbols.
- DeviceKit's sources (5.9.0 checkout) contain no `URLSession`, `URLRequest`, `NWConnection` or `import Network`.

**How the keyboard reaches the app:**
- It opens `dictus://` through `extensionContext` (`KeyboardState.swift`).
- The URL (`KeyboardDictationURL.swift`) carries only `source=keyboard`, an optional `intent=prepare` and the host app's identifier. No text.
- Everything else crosses through the App Group container, on the device.

**What the app itself sends:**
- Model files and metadata, as GET requests to Hugging Face (`ModelRepoDownloader`, `BackgroundModelDownloadService`).
- StoreKit, for purchases.
- Pages the user taps open (terms, privacy, GitHub).
- WhisperKit is always created with `download: false`, and FluidAudio loads from its local cache.
- Text leaves the app only through share sheets the user opens: log export and sharing a transcript.
- No in-app feedback submission exists in the code yet (#565 is not built).

**Privacy declarations:**
- `DictusKeyboard/PrivacyInfo.xcprivacy` and `DictusApp/PrivacyInfo.xcprivacy` both declare an empty `NSPrivacyCollectedDataTypes` and `NSPrivacyTracking = false`.
- `PRIVACY.md` states the App Store label as "Data Not Collected" / « Données non collectées ».
- `RequestsOpenAccess = true` in `DictusKeyboard/Info.plist`. Neither Info.plist has an `NSAppTransportSecurity` exception.

### Inferred, not measured
- "Can any of it run in the keyboard": no networking code is compiled or linked into the keyboard, so none can run there. This conclusion comes from source, project and symbols. I did not capture the keyboard's traffic at runtime.
- The keyboard uses Apple's on-device frameworks: FoundationModels for polish and Translation (#361, #648). Whether iOS fetches language assets for them is iOS's business, not a Dictus code path. I did not audit Apple's behaviour.
- I did not check the App Store Connect App Privacy questionnaire itself. I only checked the repo's statements of it.

### Side findings (not changed in this PR)
- The brief says *"the only networking code in the shared core is the model download"*. More exactly, the DictusCore library contains no networking at all: the download code is in DictusApp.
- `PRIVACY.md` (dated 2026-03-17) is loose in places:
  - It says "without an internet connection", although models are downloaded.
  - It says Full Access is used "solely" for the microphone, which is not how the new copy (and the code) describe it.
  - Its list of locally stored data omits the on-device learned words.
- `PRD.md:572` still mentions "user-initiated API calls (smart modes)". No such code exists.
